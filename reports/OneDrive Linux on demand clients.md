# Building Windows-Grade OneDrive Placeholders on Linux

No established Linux client reproduces the Windows Files On-Demand triad of online-only placeholders with real sizes, per-item "Always keep on this device", and "Free up space", together with file-manager status icons, so the gap you want to fill is real as of November 2026. The two mature open-source options each cover half of it: abraunegg/onedrive has the best Microsoft Graph coverage but is a full-mirror sync client whose on-demand branch went "On Hold" on 11 November 2026, while jstaf/onedriver is on-demand over FUSE but has no pinning, no status icons, no SharePoint and a largely absent maintainer. The mechanism to build on is FUSE, because it is the only one that works unprivileged on any filesystem; the kernel's purpose-built alternative, fanotify pre-content events (Linux 6.14+), needs CAP_SYS_ADMIN and suits only an optional later backend. The many-file-managers problem is solved the way Dropbox, Nextcloud and Insync solve it: a desktop-agnostic daemon owns all state and exposes a local socket, and thin per-file-manager adapters only draw emblems and send commands, since hydration happens below the file manager in the filesystem layer. Two Graph API changes shape the design from day one: `sharedWithMe` stops returning data after November 2026, and pre-authenticated download URLs, which today's ranged-read hydration depends on, retire on 1 April 2027. Because the client must sync a user-selected set of SharePoint document libraries as well as the user's own OneDrive, the requirement narrows the field further: of the on-demand clients only rclone reaches SharePoint, and it has no placeholder states, so the engine must treat every drive as an independent sync root under one sign-in from the start. Library sync needs only the `Files.ReadWrite.All` scope once a drive ID is known, and the real obstacle is tenant policy: SharePoint's unmanaged-device controls cut off app access from machines that are not Intune-compliant, which describes most Linux desktops. On Omarchy every piece needed for a first version is already installed (Nautilus 51 with nautilus-python, FUSE 3, a Quickshell tray and notification daemon, gnome-keyring), but Nautilus's days as the Omarchy default have been publicly numbered, which is the strongest argument for investing in the daemon protocol and keeping each adapter thin. This report rests on documentation, READMEs and issue trackers; no candidate's source code was audited.

## Two mature clients exist and neither delivers the Windows triad

The landscape splits into two serious open-source projects, three generic or desktop-bundled tools, three closed products, and a wave of very young imitators of exactly the feature you want. **abraunegg/onedrive** (D, GPL-3.0, about 13,000 stars, v2.5.12 released 24 October 2026) is the reference client: it covers Personal, Business, SharePoint libraries and shared folders, gets near-real-time remote changes over native WebSockets, supports Intune SSO, and has only around ten open issues ([README](https://github.com/abraunegg/onedrive), [GitHub API](https://api.github.com/repos/abraunegg/onedrive)). Its own README lists Windows-style on-demand as missing. The feature request dates from December 2019; a draft FUSE implementation (PR #3600, 67 commits, with an architecture decision record titled "FUSE overlay and local storage") exists, but the milestone slipped four times and the issue moved from "In Progress" to "On Hold" on 11 November 2026 ([Issue #757](https://github.com/abraunegg/onedrive/issues/757), [PR #3600](https://github.com/abraunegg/onedrive/pull/3600)). The reason for the hold is not stated on the issue page, and the ADR was not read for this report; it is the single most valuable unread document for your project.

**jstaf/onedriver** (Go, GPL-3.0, about 2,500 stars) is the opposite trade: a FUSE network filesystem that downloads files only when a program opens them, but loads files into memory, recommends rclone for multi-gigabyte transfers, and warns that file managers can download whole directories to build thumbnails ([README](https://github.com/jstaf/onedriver)). Its Windows-parity gaps are all long-open issues: "Always keep on this device" (#274, 2022), status indicator and free-up-space (#407), SharePoint/Teams drives (#107, open since 2021) and shared items (#70, open since 2020) ([issues](https://github.com/jstaf/onedriver/issues?q=is%3Aissue+is%3Aopen+sort%3Areactions-%2B1-desc)). Maintenance is sporadic: the last push was the v0.15.0 release on 31 January 2026, and when authentication broke across distributions in late April 2026 the thread drew no maintainer response, while Debian 13 kept shipping the broken v0.14.1 ([#478](https://github.com/jstaf/onedriver/issues/478)). Its history also includes file corruption introduced in v0.14.0 and fixed in v0.14.1 ([Releases](https://github.com/jstaf/onedriver/releases)).

rclone is the best-engineered cache of the group: `--vfs-cache-mode full` keeps sparse cache files and tracks which byte ranges are present, uploads on close, and resumes pending uploads after a crash, but it offers no per-file pin or state interface, and it polls for remote changes every minute by default ([rclone mount docs](https://rclone.org/commands/rclone_mount/)). Its OneDrive backend does not support "Shared with me" and reports listing failures around 100,000 files per folder ([rclone OneDrive docs](https://rclone.org/onedrive/)). The desktop-bundled routes are browse-only and brittle: gvfs's backend has documented crashes on listing and 401 errors for some accounts ([Ubuntu bug 2064147](https://lists.ubuntu.com/archives/ubuntu-sponsors/2025-January/083007.html), [gvfs #736](https://gitlab.gnome.org/GNOME/gvfs/-/issues/736)), and kio-onedrive builds only with clang 18+ and ships a client ID tied to its author's personal account ([kde-devel](https://mail.kde.org/pipermail/kde-devel/2026-January/004101.html)). Microsoft offers nothing: no announcement or roadmap for a Linux client was found, and its community channels point Linux users to abraunegg, rclone, Insync and ExpanDrive ([Tech Community](https://techcommunity.microsoft.com/discussions/microsoft-365/onedrive-on-linux/1318644)). That is an absence of any announcement, not a statement that one will never ship.

The most telling signal is the wave of more than ten "Files On-Demand for Linux" repositories created between March and November 2026, none with more than 17 stars and none packaged for the AUR ([GitHub search](https://api.github.com/search/repositories?q=onedrive+%22on-demand%22+linux+pushed:>2025-01-01&sort=stars)). They show demand, and two are useful specifications of the Windows experience on Linux. **twodrive** (Rust, MIT, GNOME) ships a daemon, CLI, Nautilus extension and tray with five emblem states and a "release pending" state for files that are still uploading, and its README candidly lists the edge cases a clone must define, such as pins not propagating to newly discovered children ([twodrive README](https://github.com/LumiaBlack51/twodrive)). **konedrive** (Rust, GPL-3.0-or-later, KDE) adds the one idea no mature client has: its Dolphin plugin fetches previews from OneDrive itself, so thumbnails never force a download ([konedrive README](https://github.com/kartas39/konedrive)). Neither is a proven foundation.

The SharePoint requirement is the sharpest discriminator in this table, because on-demand access and library sync never appear together in a mature client. abraunegg syncs SharePoint libraries and fixed its WebSocket notifications for them in v2.5.10, but mirrors them in full ([Releases](https://github.com/abraunegg/onedrive/releases)). It also handles them one at a time: each library needs its own configuration directory, sync folder, re-authorisation and copied service unit, found by running a command-line site-name lookup, and its guide warns of data loss when desktop indexers touch the synced files ([abraunegg SharePoint guide](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/sharepoint-libraries.md)). rclone can target a SharePoint site or a drive ID as a `documentLibrary` drive type and mount it, one remote per library, without pin or status semantics ([rclone OneDrive docs](https://rclone.org/onedrive/)). Neither has an in-app library picker beyond a site-name search, and neither presents one account with many libraries the way Windows does. Insync advertises a SharePoint tab with selective sync on Linux, seen only as a marketing snippet ([Insync](https://www.insynchq.com/i/onedrive/sharepoint)). onedriver has neither, konedrive supports personal accounts only, and the one new project claiming OneDrive plus SharePoint with on-demand files, craftDriver, is days old with two stars ([GitHub search](https://api.github.com/search/repositories?q=onedrive+%22on-demand%22+linux+pushed:>2025-01-01&sort=stars)). ExpanDrive's SharePoint support is a vendor claim that was not verified.

There is no ideal fork base, and I would start fresh while borrowing designs. Forking onedriver gives a working FUSE core fastest but inherits whole-file-in-memory handling, embedded-WebKit sign-in and 150-plus open issues with nobody to merge upstream. Forking abraunegg means retrofitting a mirror-sync engine written in D, and its on-demand branch remains a competitor risk if it resumes. Licence matters here: abraunegg, onedriver and konedrive are GPL-3.0, so porting their code makes your client GPL-3.0, whereas rclone and twodrive are MIT.

## FUSE stacked over a real directory is the mechanism to build on

FUSE is the only mechanism that mounts unprivileged (through the setuid `fusermount3` helper), is independent of the backing filesystem, and is what every shipping Linux on-demand product uses: rclone, onedriver, pCloud, SeaDrive, and now Nextcloud ([kernel FUSE docs](https://docs.kernel.org/filesystems/fuse/fuse.html)). Vendors without a FUSE layer simply do not offer transparent on-demand files on Linux; Dropbox's Smart Sync remains Windows and macOS only ([Dropbox forum](https://www.dropboxforum.com/t5/Dropbox-ideas/When-will-Smart-Sync-work-on-linux/idi-p/262171)). The alternative that needs no kernel support at all, suffix stub files such as Nextcloud's `.nextcloud`, is not transparent to applications or the shell, and its own maintainers called it not stable enough for daily use ([nextcloud/desktop #3668](https://github.com/nextcloud/desktop/issues/3668)).

The kernel's purpose-built answer is fanotify pre-content events. `FAN_PRE_ACCESS`, merged in Linux 6.14, notifies a daemon before a byte range of a file is read, including through mmap page faults, so the daemon can fill a sparse stub and then allow the access; it is enabled on ext4, btrfs and xfs ([fanotify_mark(2)](https://man7.org/linux/man-pages/man2/fanotify_mark.2.html), [LWN](https://lwn.net/Articles/998968/)). It is the closest Linux analogue to the Windows cloud-files filter driver, and hydrated files are ordinary files at native speed with no mountpoint. Three facts rule it out as your primary architecture. **It requires CAP_SYS_ADMIN**, and unprivileged fanotify explicitly cannot request permission events ([fanotify_init(2)](https://man7.org/linux/man-pages/man2/fanotify_init.2.html)), so a per-user client needs a root helper. Directory population on demand was left out of the 6.14 merge, and whether follow-up patches landed could not be confirmed ([commit 4f8afa33](https://github.molgen.mpg.de/mariux64/linux/commit/4f8afa33817a6420398d1c177c6e220a05081f51)). And the design depends on the daemon running: by my reading of the mechanism, a stub read while the daemon is down returns zeros with no error, where a dead FUSE mount fails loudly. Its one known large user is Meta, internally; no desktop sync client using it was found. Your machine's 7.2 kernel is new enough, so this is a privilege and maturity problem, not a version problem.

The pattern I recommend is **FUSE stacked over the real sync directory**, as OpenCloud's openvfs does: files and their state live as ordinary files plus extended attributes on the user's own filesystem, and FUSE only interposes on `open()` to block until the sync client has fetched the content ([openvfs](https://github.com/opencloud-eu/openvfs)). Nextcloud integrated openvfs in Desktop 35 in autumn 2026, closing a five-year-old "virtual files on Linux" issue, though it is still experimental and absent from the Flatpak ([nextcloud/desktop #3668](https://github.com/nextcloud/desktop/issues/3668)). Two properties make this the right seam. State survives a daemon crash and stays inspectable. And the on-disk format, a sparse file plus xattrs, is the same one a fanotify backend would use, so the interposition layer can be swapped later where privileges allow. Combine it with rclone's range-tracked sparse caching rather than onedriver's whole-file model.

FUSE's weaknesses are specific and must be designed for. The two newest accelerators do little for an unprivileged daemon: passthrough to a backing file still requires CAP_SYS_ADMIN in the 7.2 documentation, and FUSE-over-io_uring needs a module parameter set by root ([passthrough docs](https://docs.kernel.org/7.2/_sources/filesystems/fuse/fuse-passthrough.rst.txt), [libfuse](https://raw.githubusercontent.com/libfuse/libfuse/master/doc/README.fuse-io-uring)). No benchmark quantifying the cost on current kernels was found. Offline behaviour is the daemon's job: the request timeouts added in Linux 6.15 are opt-in and abort the whole connection, so they are a dead-daemon safety net and not a way to return an error for one read ([6.15 fuse pull](https://lkml.rescloud.iu.edu/2504.0/00453.html)). The daemon must answer quickly with an errno when the network is down. Sandboxes complicate visibility: snap's confinement fails on user FUSE mounts ([snapcraft forum](https://forum.snapcraft.io/t/can-interfaces-define-per-user-bind-mounts/501/18)), and FUSE mounts in the runtime directory are awkward for Flatpak apps ([KDE bug 434917](https://bugs.kde.org/show_bug.cgi?id=434917)), which argues for mounting inside the home directory.

The state model to copy is the one Windows and macOS share: hydration (placeholder, partial, full) and pin policy (pinned, unpinned, unspecified, excluded, inherit) are separate axes, plus an in-sync flag. On Windows, dehydration fails if a file is pinned and requires it to be in sync, and any application may set pin state as a request the provider fulfils asynchronously ([CF_PIN_STATE](https://learn.microsoft.com/en-us/windows/win32/api/cfapi/ne-cfapi-cf_pin_state), [CfUpdatePlaceholder](https://learn.microsoft.com/windows/win32/api/cfapi/nf-cfapi-cfupdateplaceholder)). My suggested layering is a SQLite database as the source of truth, `user.*` xattrs as the public read and pin-request interface, and sparse extents as the physical cache; xattrs alone are too fragile because many tools strip them on save ([nextcloud/desktop #3668](https://github.com/nextcloud/desktop/issues/3668)). Report the cloud size as file size and only local bytes as blocks, which reproduces the Windows "size" versus "size on disk" distinction.

The dominant failure classes in existing FUSE cloud filesystems tell you where to spend effort. Write-path corruption leads onedriver's tracker: large files destroyed when manipulated, KeePassXC databases corrupted on save, renames failing before upload completes ([issues index](https://issues.ecosyste.ms/hosts/GitHub/repositories/jstaf%2Fonedriver/issues?page=2)). Writes should land in a durable local file first and upload asynchronously. The second class is unintended hydration by anything that walks the tree. FUSE cannot signal "do not hydrate for this reader" the way the Windows and macOS backends can ([wusel](https://wusel.itbh.at/wusel/0.3.0/explanation/vfs-first.html)). KDE's Baloo already refuses FUSE network mounts ([KDE Discuss](https://discuss.kde.org/t/baloo-refuses-to-index-fuse-network-mounts-e-g-rclone-with-no-opt-in-override/50530)), so the live risks are thumbnailers, previewers, backup tools and recursive grep. The mitigations I propose, identifying the calling process on each request and refusing known crawlers, a circuit breaker on mass hydration, and seeding the desktop thumbnail cache from Graph's thumbnail endpoint, are design proposals; no Linux client was found doing the first two, and only konedrive does anything like the third.

## One daemon and thin adapters solve the many-file-managers problem

Linux has no platform component for registering a sync root or drawing status icons, so the answer to "many file managers" is not a universal API but a narrow one you own. The consensus architecture across Dropbox, ownCloud/Nextcloud, Insync and the 2026 newcomer wusel is the same: **the daemon owns state and exposes a local socket; per-file-manager plugins query it and render** ([Nextcloud socketapi.cpp](https://raw.githubusercontent.com/nextcloud/desktop/master/src/gui/socketapi/socketapi.cpp), [wusel status protocol](https://wusel.itbh.at/wusel/latest/explanation/status-protocol.html)). A key simplification follows from a Nautilus limitation: extensions cannot hook file activation, so opening a placeholder cannot be an extension-level event ([wusel](https://wusel.itbh.at/wusel/0.4.0/explanation/desktop-integration.html)). Hydration therefore lives in the filesystem layer, works identically from a terminal, an editor or any file manager, and adapters become purely cosmetic and command-issuing. A file manager with no adapter still gets working on-demand files; it only lacks the icons and the right-click menu.

What each file manager can render differs widely, and the protocol should carry the full state so each adapter reduces it to what its host supports.

| File manager | Per-file emblems | Dynamic context menu | Adapter form |
|---|---|---|---|
| Nautilus, Nemo, Caja | Yes | Yes | One Python source serves all three |
| Dolphin | Yes | Yes | Two compiled C++ plugins tied to the KDE Frameworks major version |
| Thunar | No emblem function in the public API | Yes | Menu-only plugin |
| COSMIC Files | No | User-configured static actions only | None available |
| yazi (terminal) | Status text via an async "fetcher" plugin | Keybound actions | Lua plugin |
| Flea (Omarchy) | Undocumented | Undocumented | Unknown; plugins run as separate processes |

Nautilus's GTK4 extension API is model-only: emblems, menu items, list columns and text-only property pages, with no widgets ([nautilus-python migration guide](https://gnome.pages.gitlab.gnome.org/nautilus-python/nautilus-python-migrating-to-4.html)). Nextcloud generates its Nemo and Caja extensions from its Nautilus script by string replacement, which shows one Python file covers three file managers ([Nextcloud CMakeLists](https://raw.githubusercontent.com/nextcloud/desktop/master/shell_integration/nautilus/CMakeLists.txt)). Thunar's `ThunarxFileInfo` has no emblem function ([reference](https://developer.xfce.org/thunar/ThunarxFileInfo.html)). Dolphin plugins break across framework generations; openSUSE shipped a Qt5 build of Nextcloud's plugin and overlays silently vanished ([openSUSE bug 1221923](https://lists.opensuse.org/archives/list/bugs@lists.opensuse.org/thread/MUO5Z6HLHN3L2K5ZNBSQXDANE4RGXVBZ)).

For the wire protocol, Nextcloud's socket API is worth being compatible with. It is a line-based text protocol over a Unix socket at `$XDG_RUNTIME_DIR/<AppName>/socket`, its menus are server-driven, and it already has `MAKE_AVAILABLE_LOCALLY` and `MAKE_ONLINE_ONLY` verbs, so a rebranded copy of the existing script could show "Always keep on this device" and "Free up space" on day one ([syncstate.py](https://raw.githubusercontent.com/nextcloud/desktop/master/shell_integration/nautilus/syncstate.py), [socketapi.cpp](https://raw.githubusercontent.com/nextcloud/desktop/master/src/gui/socketapi/socketapi.cpp)). Its status vocabulary (`OK`, `SYNC`, `ERROR` and a shared variant) cannot distinguish online-only from local from pinned, so your daemon needs its own richer, versioned protocol with a batch enumerate call and a change stream, with the Nextcloud dialect as a compatibility endpoint at most. Whether the stock script tolerates unknown status tokens is untested, and its licence was not checked, so a clean-room adapter of a few hundred lines is the safer path. Adapters must answer from a cache: a measured per-file query costs about 230 microseconds, roughly 46 ms for a cold 200-file folder ([wusel status protocol](https://wusel.itbh.at/wusel/latest/explanation/status-protocol.html)).

No desktop-neutral mechanism shows per-file state. GIO's `metadata::emblems` does not refresh live ([Thunar issue 630](https://gitlab.xfce.org/xfce/thunar/-/issues/630)), and libcloudproviders gives only an account-level sidebar entry and status in Nautilus and GTK file choosers, with KDE not consuming it ([libcloudproviders README](https://raw.githubusercontent.com/GNOME/libcloudproviders/main/README.md), [wusel](https://wusel.itbh.at/wusel/0.4.0/explanation/desktop-integration.html)). The genuinely neutral surfaces are the StatusNotifierItem tray, `org.freedesktop.Notifications`, sidebar bookmarks and the Secret Service for tokens. The daemon, CLI and UI should be separate processes so the toolkit is swappable.

Packaging constrains this more than toolkit choice does. Sandboxed builds of the Nextcloud client lose overlay icons and context menus in every file manager because host extension directories are outside the sandbox ([Nextcloud forum](https://help.nextcloud.com/t/sandboxed-nextcloud-desktop-client-for-linux-and-system-integration/36627)), and Nextcloud's Flatpak lacks the FUSE feature its AppImage has. Ship native packages (AUR first, then deb and rpm) with small optional sub-packages per adapter. pCloud's AppImage shows the other trap: its libfuse2 dependency must be installed by hand on Ubuntu 24.04+ ([pCloud](https://www.pcloud.com/how-to-install-pcloud-drive-linux)), so speak the FUSE protocol natively or link libfuse3.

On Omarchy, local inspection of an Omarchy 4.5.0 machine shows a first integration needs no new system dependencies. Nautilus 51.1 is the default file manager with nautilus-python 4.2.0 installed; Omarchy itself ships Nautilus Python extensions in `~/.local/share/nautilus-python/extensions/`, a first-party precedent for your adapter's form and location. `fusermount3` 3.18.3 is present, gnome-keyring owns the Secret Service, and Nautilus, GTK3 and GTK4 are all linked against libcloudproviders. Note that Waybar and Mako are gone: since Omarchy 4.0 a single Quickshell-based shell provides the bar, the tray and the notification daemon ([Omarchy v4.0.0 release notes](https://github.com/basecamp/omarchy/releases/tag/v4.0.0)). The tray needed a custom workaround for submenus, so keep the tray menu flat. Omarchy's own apps are Qt Quick, which makes Qt6/QML the natural choice for a settings and activity window and ports unchanged to KDE; a Quickshell bar plugin is an Omarchy-native extra. The hydration risk is concrete on a stock install: the `localsearch` indexer autostarts, the `sushi` previewer and several thumbnailers are installed, and "local-only" thumbnailing has historically still covered kernel-mounted paths ([Launchpad bug 293311](https://bugs.launchpad.net/ubuntu/+source/nautilus/+bug/293311)). Finally, DHH said on 11 September 2026 that Nautilus's days as the Omarchy default are numbered, naming the new Flea file manager as one candidate; this is reported through a secondary article, and Flea's plugin interface is undocumented ([Starry Hope](https://www.starryhope.com/linux/flea-file-manager-omarchy/)).

## Graph permits the client but sets two near-term deadlines

Microsoft's guidance for third-party sync engines is to use Graph, and delta queries, upload sessions and ranged downloads are sufficient to build a full on-demand client ([SharePoint throttling guidance](https://learn.microsoft.com/en-us/sharepoint/dev/general-development/how-to-avoid-getting-throttled-or-blocked-in-sharepoint-online)). The catch is that the documented ranged-read mechanism is about to change. Today `GET .../content` returns a 302 redirect to a short-lived pre-authenticated URL, and the `Range` header must be sent to that URL, not to `/content` ([download docs](https://learn.microsoft.com/en-us/graph/api/driveitem-get-content?view=graph-rest-1.0)). Message Center post MC1492958 (9 October 2026, read through a third-party mirror) says **Microsoft will retire pre-authenticated URLs in SharePoint Online and OneDrive on 1 April 2027**; affected APIs include download, upload sessions and thumbnails, and apps must send bearer tokens and handle direct content responses ([MC1492958 mirror](https://mc.merill.net/message/MC1492958)). rclone corroborates the date for Business and SharePoint ([rclone docs](https://rclone.org/onedrive/)). Two things are unknown: whether `Range` will be honoured on `/content` afterwards, and whether personal accounts are in scope. Test the first empirically before committing to range-based hydration, check the status code on every read because the server may return 200 with the full body, and decide per response whether an upload URL needs an `Authorization` header.

The second deadline has arrived: `sharedWithMe` "will stop returning data" after November 2026 ([sharedWithMe docs](https://learn.microsoft.com/en-us/graph/api/drive-sharedwithme?view=graph-rest-1.0)). The durable route to shared content is "Add shortcut to My files", which is where rclone and abraunegg already steer users, and even Microsoft's own client cannot sync the "Shared with me" view of a work account ([OneDrive restrictions](https://support.microsoft.com/en-us/office/restrictions-and-limitations-in-onedrive-and-sharepoint-64883a5d-228e-48f5-b3d2-eb39e07630fa)).

The sync primitives carry rules that become engine invariants. Track items by ID, never path, because delta omits paths and a folder rename does not return its descendants; use the last occurrence of an item in a feed; handle `410 Gone` resyncs by keeping both copies when unsure ([delta docs](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0)). Business delta omits `cTag`, so detect content changes with eTag, size and `quickXorHash`, the only hash guaranteed on both account types ([hashes](https://learn.microsoft.com/en-us/graph/api/resources/hashes?view=graph-rest-1.0)). Upload fragments must be multiples of 320 KiB and under 60 MiB, and whole files are always re-sent ([createUploadSession](https://learn.microsoft.com/en-us/graph/api/driveitem-createuploadsession?view=graph-rest-1.0)). For change notification, Graph's socket.io endpoint works with delegated permissions on personal and work accounts and avoids the public HTTPS endpoint webhooks require ([socketIo docs](https://learn.microsoft.com/en-us/graph/api/subscriptions-socketio?view=graph-rest-1.0)); use it as a wake-up signal followed by a delta call, with slow polling as fallback.

Throttling shapes the read path. Business accounts get 3,000 requests per five minutes per user, a delta call with a token costs one resource unit, any permission read costs five, and only `Retry-After` is a reliable back-off signal; traffic with a User-Agent in the `ISV|Company|App/Version` format is prioritised ([throttling guidance](https://learn.microsoft.com/en-us/sharepoint/dev/general-development/how-to-avoid-getting-throttled-or-blocked-in-sharepoint-online)). A filesystem that issues one request per small `read()` will hit the cap, so read-ahead and chunk caching are required. No throttling numbers are published for personal accounts.

Known quirks belong in the engine from the start. SharePoint libraries silently modify uploaded Office files, so record the server's post-upload hash as the baseline or the engine will loop ([rclone docs](https://rclone.org/onedrive/)). The namespace is case-insensitive, names have reserved characters and words, and 400 characters is the safe path limit. Since June 2025 Personal accounts return drive IDs in mixed case; abraunegg normalises them to lowercase ([onedrive-api-docs #1902](https://github.com/OneDrive/onedrive-api-docs/issues/1902)). Timestamps are whole seconds only ([abraunegg usage](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/usage.md)).

Authentication is the most fragile area in existing clients. onedriver's embedded WebKit window often renders blank and broke twice on Microsoft-side changes; abraunegg moved to a system browser with a loopback redirect, device-code flow and the Intune identity broker ([abraunegg usage](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/usage.md)). Follow abraunegg. Its docs say device-code flow is not allowed for personal accounts, a single-project claim. Refresh tokens last 90 days and roll on each use ([refresh tokens](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens)). Both rclone and abraunegg ship a shared default client ID with a user override, and abraunegg states its scopes need no admin consent ([application-security.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/application-security.md)). The tenant policies that block third-party clients, chiefly unmanaged-device access controls, are covered in the SharePoint section below.

The Microsoft APIs Terms of Use contain no clause against a third-party sync client, but Microsoft may change or discontinue the APIs at any time, and the terms prohibit working around technical limitations and bar applications from storing computer system back-up data in OneDrive ([Terms of Use](https://learn.microsoft.com/en-us/legal/microsoft-apis/terms-of-use)). Stay on documented Graph endpoints and do not market the client as a system backup tool. Trademark guidelines were not read; a distinct product name with a "for OneDrive" descriptor is the conservative choice.

On parity, most Windows features are local behaviour over the same cloud operations. Placeholders, pinning, free-up-space, automatic eviction, pause, multiple accounts and SharePoint library sync are feasible; this is my assessment, and the Windows feature behaviours themselves were not sourced. Three things are out of reach: Personal Vault fails to list through the API ([rclone docs](https://rclone.org/onedrive/)), block-level differential upload has no Graph equivalent, and Office desktop co-authoring depends on interfaces outside public Graph. Microsoft's icon vocabulary (cloud outline, green tick, solid green tick, sync arrows, person, red cross) is documented and maps directly onto your emblem set ([OneDrive icons](https://support.microsoft.com/en-us/office/what-do-the-onedrive-icons-mean-11143026-8000-44f8-aaa9-67c985aa49b3)).

## SharePoint libraries make every drive a separate sync root

Syncing the user's OneDrive plus a chosen set of SharePoint libraries is feasible on public Graph, and the API treats a library as just another drive. Delta is requested per drive, at `/drives/{id}/root/delta`, `/sites/{id}/drive/root/delta` or `/groups/{id}/drive/root/delta`, and returns that drive's hierarchy only ([delta docs](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0)). The architectural consequence is that **the unit of sync is the drive, not the account**. The engine's core object should be a "mounted drive": a drive ID, an optional root item inside it, a local path and a delta token, with the state store keyed by drive ID and item ID from the first commit. This is also the clearest opening against the existing clients. abraunegg needs a separate configuration directory, a fresh authorisation, a resync and a hand-copied service unit for every library, and rclone needs one remote per library ([abraunegg SharePoint guide](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/sharepoint-libraries.md), [rclone docs](https://rclone.org/onedrive/)). One sign-in and one daemon holding many drives is what Windows presents and what no Linux client offers.

### Files scopes are enough to sync a library; site scopes only buy search

Driveitem delta on a work account accepts the `Files.*` scopes as well as `Sites.*`, so **`Files.ReadWrite.All` is sufficient to sync any library the user can reach once the client knows its drive ID** ([delta docs](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0)). `Sites.Read.All` is needed only for discovery by site: both `GET /sites?search=` and `GET /me/followedSites` require it, neither works for personal accounts, and Microsoft warns that followed sites "might return incorrect results" ([site search](https://learn.microsoft.com/en-us/graph/api/site-search?view=graph-rest-1.0), [followed sites](https://learn.microsoft.com/en-us/graph/api/sites-list-followed?view=graph-rest-1.0)). There is no single call that lists every library a user can reach. Two discovery routes work without the site scope. A pasted sharing URL resolves through `GET /shares/{encoded-url}` to a drive item whose parent reference carries the drive ID ([shares docs](https://learn.microsoft.com/en-us/graph/api/shares-get?view=graph-rest-1.0)). A Teams channel resolves through `filesFolder`, whose least-privileged permission is `Files.Read.All` ([filesFolder docs](https://learn.microsoft.com/en-us/graph/api/channel-get-filesfolder?view=graph-rest-1.0)). The add-library flow I recommend is therefore paste a link, browse Teams, or type a drive ID, with site search as an extra that asks for `Sites.Read.All` only when the user opens it; rclone's option to drop that scope for tenants that refuse it shows the same split in practice ([rclone docs](https://rclone.org/onedrive/)). This replaces abraunegg's default request for `Sites.ReadWrite.All` with a narrower baseline.

Three details of these routes matter. The header `Prefer: redeemSharingLink` permanently grants the user access, exactly as clicking the link would, so a preview step should use `redeemSharingLinkIfNecessary` and redeem only on confirmation ([shares docs](https://learn.microsoft.com/en-us/graph/api/shares-get?view=graph-rest-1.0)). After Microsoft's private-channel migration, `filesFolder` for a private channel returns a drive root and new private channels no longer get a same-named folder, so the client must take whatever item the call returns per channel and never assume a subfolder of the team's library ([filesFolder docs](https://learn.microsoft.com/en-us/graph/api/channel-get-filesfolder?view=graph-rest-1.0)). And whether a plain browser URL for a library, as opposed to a sharing link, always resolves through `/shares` was not confirmed. The belief that private and shared channels each live in their own site, and the standard calls for listing a site's libraries and a user's joined teams, come from the researcher's prior knowledge and were not re-verified.

Narrower consent exists but does not suit a default. The Selected scope family, including `Lists.SelectedOperations.Selected` for a single library, now supports delegated sign-in, but it grants nothing until an admin or owner explicitly authorises the app on each site or library, and site search does not work under it ([Selected permissions](https://learn.microsoft.com/en-us/graph/permissions-selected-overview)). It is a credible "enterprise mode" for security-conscious tenants, not a consumer flow. Which of these scopes users can consent to without an admin was not verified against the permissions reference.

### Tenant policy, not scopes, is what blocks a Linux client

The real blocker is on the tenant side. SharePoint's unmanaged-device controls define unmanaged as "not hybrid AD joined or compliant in Intune", which describes almost every Linux machine. Under limited access, such users get browser-only access "with no ability to download, print, or sync files" and cannot reach content through apps; under block access they get "Access Denied" ([unmanaged devices](https://learn.microsoft.com/en-us/sharepoint/control-access-from-unmanaged-devices)). The policy can be tenant-wide, per site or driven by a site's sensitivity label, can take up to 24 hours to apply, and exempts only app-only services, not a client acting for a signed-in user. A tenant can also refuse the app outright; rclone documents error AADSTS65005 for this case ([rclone docs](https://rclone.org/onedrive/)). The client therefore needs a per-library "blocked by organisation policy" state distinct from a sync error, and one library failing must never stall the others. The known way to satisfy device-compliance policy on Linux is abraunegg's Intune SSO mode, which obtains tokens through the Microsoft identity broker on an enrolled machine ([abraunegg config options](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/application-config-options.md)). Two things are unknown: the exact errors Graph returns when these policies bite, and the effect of the "sync only on domain-joined computers" setting, which Microsoft documents as an Active Directory setting for its own sync app and says nothing about for Graph clients ([domain restriction](https://learn.microsoft.com/en-us/sharepoint/allow-syncing-only-on-specific-domains)). Both need testing against a real tenant.

### Sync a library as its own root; treat shortcuts as a compatibility feature

Windows offers two models. The Sync button creates a per-device root in a folder named after the organisation; "Add shortcut to My files" places a link inside the user's own OneDrive that follows the account to every device. Microsoft recommends shortcuts "as the more versatile option" ([Sync in SharePoint and OneDrive](https://learn.microsoft.com/en-us/sharepoint/sharepoint-sync)). For a Graph client I recommend the opposite priority. A library synced as its own root is one drive with one delta stream. A shortcut is a stub in the user's drive pointing at a folder in another drive, so the client must run a second change stream against the target drive and graft the results under the stub's path; because delta is reliably available only from a drive root, a shortcut to one folder of a large library means a root delta on the whole library filtered locally. The stub itself is unreliable: a 2021 report that shortcuts to SharePoint are absent from business `/delta` was closed in a repository clean-up without a fix ([onedrive-api-docs #1427](https://github.com/OneDrive/onedrive-api-docs/issues/1427)), and rclone documents "drive id appears to be malformed" errors when listing through shortcuts ([rclone docs](https://rclone.org/onedrive/)). abraunegg does sync business shortcuts since its v2.5.0 rewrite ([business shared items](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/business-shared-items.md)), but how it discovers them was not checked in its source, and an undocumented request header said to reveal them rests on a single forum snippet. The shape of a shortcut stub in delta today needs a live test.

Shortcuts cannot be skipped, since they are now the only durable route to shared folders, but their delete semantics are the riskiest code in the client. Removing a shortcut removes it only for the user, whereas deleting the folder "deletes it from everyone's OneDrive", and Microsoft documents data-loss cases in its own client ([Add shortcuts](https://support.microsoft.com/en-us/office/add-shortcuts-to-shared-folders-in-onedrive-for-work-or-school-d66b1347-99b7-4470-9360-ffc048d35a33)). Three rules follow: removing a mount directory must never become a recursive remote delete; "Remove shortcut" and "Stop syncing this library" must be explicit menu actions; and the same folder reachable both as a synced library and through a shortcut must be detected by drive and item ID and merged or refused. A shortcut's local name comes from the stub, because renaming a shortcut is private to the user. Folders shared from outside the organisation cannot be synced at all; abraunegg attributes this to Graph not presenting them ([business shared items](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/business-shared-items.md)).

### Read-only libraries and rewritten files need engine rules, not flags

Microsoft's own client syncs a library read-only when it requires check-out, has validation columns or restricts draft visibility, and its sync article adds required columns as a cause; such files show a lock icon and local changes "won't sync" ([OneDrive restrictions](https://support.microsoft.com/en-us/office/restrictions-and-limitations-in-onedrive-and-sharepoint-64883a5d-228e-48f5-b3d2-eb39e07630fa), [Sync SharePoint and Teams files](https://support.microsoft.com/en-us/office/sync-sharepoint-and-teams-files-with-your-computer-6de9ede8-5b6e-4503-80b2-6190f3354a88)). A Linux client should copy the behaviour and improve on it: Windows silently strands edits, whereas a filesystem layer can refuse the write up front with a read-only error. Detection is best done once per library from its settings and the user's role, not per item, since permission reads cost five resource units each. The Graph calls for reading check-out state were not fetched, and how an upload behaves in a forced-check-out library is unverified. Items the user may see but not download return HTTP 403 and should be skipped individually ([business shared items](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/business-shared-items.md)).

Server-side rewriting is the most damaging library behaviour, and every existing client handles it with a switch: rclone tells users to ignore size and checksum, abraunegg offers options to skip validation or to upload again as a new version ([rclone docs](https://rclone.org/onedrive/), [abraunegg config options](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/application-config-options.md)). The cause is described as SharePoint "property promotion" embedding column data in Office, email and TIFF files, on the strength of a community answer and not primary documentation. The design fix is to store two hashes per item, the local content at upload and the server's value afterwards, and to call the file in sync while both still hold. An on-demand client has an advantage here: the uploaded file stays hydrated with the local bytes and only a later genuine server change triggers a re-download. abraunegg's SharePoint guide carries a data-loss warning that names desktop indexers and editors that save by delete-and-replace as triggers, which makes the thumbnailer and indexer defence described earlier a data-safety requirement inside library roots, not only a bandwidth one ([abraunegg SharePoint guide](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/sharepoint-libraries.md)). abraunegg also schedules periodic full scans that bypass the stored delta link, a sign that delta alone has not been fully trusted on these drives; a low-priority reconciliation pass per mounted drive is prudent.

Names must be validated before upload, because Linux permits what SharePoint forbids: the reserved characters and device names, names starting `~$`, `_vti_` anywhere, `forms` at a library root, and names differing only by case ([OneDrive restrictions](https://support.microsoft.com/en-us/office/restrictions-and-limitations-in-onedrive-and-sharepoint-64883a5d-228e-48f5-b3d2-eb39e07630fa)). The 400-character path limit is counted on the server side, and my reading is that the site and library segments consume part of it, so the usable budget differs per library; the counting rule itself was not fetched. Microsoft recommends no more than 300,000 items across everything a user syncs, "even if you don't sync them all", so adding a library should show its item count and warn as the total approaches that figure. Behaviour under retention labels and legal holds was not found and must be tested.

### Several roots share one tenant budget and one local layout

Windows shows the user's own drive as "OneDrive - Contoso", with shortcuts inside it, and puts every synced library from that tenant under a second root named after the organisation ([Sync SharePoint and Teams files](https://support.microsoft.com/en-us/office/sync-sharepoint-and-teams-files-with-your-computer-6de9ede8-5b6e-4503-80b2-6190f3354a88), [Add shortcuts](https://support.microsoft.com/en-us/office/add-shortcuts-to-shared-folders-in-onedrive-for-work-or-school-d66b1347-99b7-4470-9360-ffc048d35a33)). The Linux equivalent is `~/OneDrive - <Org>` per work account and `~/<Org>/` holding one directory per library. The naming of library folders inside the organisation root, commonly seen as site name then library name, was not stated on the pages read. Two accounts in the same tenant would collide on the organisation folder and need a disambiguation rule. Whether these are separate FUSE mounts or subtrees of one is an implementation choice the research did not test; I lean to as few mountpoints as the layout allows, to have one place to enforce hydration policy. Stopping a library should leave local copies in place, as Windows does. The emblem set gains two members: a lock for read-only content and a chain-link folder for shortcuts, the latter documented on Microsoft's icon page ([OneDrive icons](https://support.microsoft.com/en-us/office/what-do-the-onedrive-icons-mean-11143026-8000-44f8-aaa9-67c985aa49b3)). The file-manager protocol already fits, since Nextcloud's daemon registers each sync root separately ([socketapi.cpp](https://raw.githubusercontent.com/nextcloud/desktop/master/src/gui/socketapi/socketapi.cpp)), and because Nautilus shows every cloud-provider sidebar entry with no way to hide one, an entry per account is safer than one per library ([GNOME Discourse](https://discourse.gnome.org/t/per-entry-visibility-control-for-cloudproviders-in-nautilus/33836)).

Throttling is a shared budget across roots. Limits are per user and per app per tenant, starting at 1,250 resource units per minute for tenants under 1,000 licences, and Microsoft names sync engines among the apps it expects to throttle ([throttling guidance](https://learn.microsoft.com/en-us/sharepoint/dev/general-development/how-to-avoid-getting-throttled-or-blocked-in-sharepoint-online)). One scheduler must own the request budget for the tenant; per-drive workers backing off independently will collectively overrun it. The April 2027 URL retirement lands squarely here too: apps opening SharePoint URLs directly will need a token for the SharePoint resource, which the same refresh token can obtain, and admins can move specific app IDs to the new behaviour early ([MC1492958 mirror](https://mc.merill.net/message/MC1492958), [refresh tokens](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens)). Each drive can have its own socket.io notification endpoint ([socketIo docs](https://learn.microsoft.com/en-us/graph/api/subscriptions-socketio?view=graph-rest-1.0)); whether a business drive can be watched below its root remains open, with a search summary suggesting it cannot. One contractual point also remains open: the API terms bar applications from enabling storage of "team, organization, or departmental level data" in Microsoft OneDrive ([Terms of Use](https://learn.microsoft.com/en-us/legal/microsoft-apis/terms-of-use)). As written this concerns what is put into OneDrive, not syncing a SharePoint library that already holds team data, but I did not find Microsoft's interpretation.

## Conclusion

The research changes the shape of the question. "Supporting many file managers" turns out to be the cheap part: once hydration lives in the filesystem layer, every file manager, terminal and application gets on-demand files for free, and an adapter is a few hundred lines of emblem-drawing that can be added per desktop as demand appears. The expensive, differentiating work is elsewhere, in a write path that never corrupts, a defence against thumbnailers and indexers that no Linux client has yet built, and a Graph layer that survives Microsoft's changes. That suggests the build order: daemon, a state store built around mounted drives, and CLI first, proving the engine on the personal drive and one SharePoint library synced as its own root under a single sign-in; a stacked FUSE layer second, with read-only enforcement for locked libraries; the Nautilus adapter third; and then shortcuts, site search, and adapters for Dolphin, yazi and whatever replaces Nautilus on Omarchy. Shortcuts come late on purpose: they carry the worst delete semantics and the least reliable API surface, and a library synced as a root covers the stated requirement without them.

The SharePoint findings also move the main adoption risk from engineering to policy. A client can be correct and still be locked out of a tenant that restricts unmanaged devices, so the first test against a work account should be on a tenant with those controls enabled, and Intune broker sign-in belongs on the roadmap as the answer for such organisations and not as an enterprise extra.

Four checks should precede any architecture commitment, because each could change it. Run a live test of how a business shortcut stub appears in delta and what Graph returns under unmanaged-device and domain-join restrictions, since the documentation is silent on all three. Read abraunegg's FUSE ADR in PR #3600 and find out why the work was put on hold, since it either reveals a pitfall or signals a returning competitor. Test how `Range` behaves on authenticated `/content` requests for both account types ahead of April 2027, since range-based hydration depends on it. And ask the Flea author early for a per-file status hook, since Omarchy's default file manager is the one integration surface you do not control. The existence of ten near-identical hobby projects in three months says the window for a well-engineered client is open, but also that a durable one will be distinguished by data safety and maintenance, not by the feature list.
