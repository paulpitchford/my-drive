# ADR-0010: Auth uses our own app registration, the system browser with a loopback redirect, and the Secret Service

- **Status:** Accepted
- **Date:** 2026-11-14
- **Depends on gates:** G5 (see `docs/architecture/overview.md`)

## Context

Sign-in is the most fragile area in existing Linux clients. onedriver's embedded WebKit
window often renders blank and broke on Microsoft-side changes (token format, AADSTS70000);
its auth broke again across distributions in April 2026 with no maintainer response
([onedriver issues](https://github.com/jstaf/onedriver/issues?q=is%3Aissue+is%3Aopen+sort%3Areactions-%2B1-desc),
[#478](https://github.com/jstaf/onedriver/issues/478)). abraunegg moved to a system browser
with a loopback redirect, a manual paste fallback, device-code flow and the Intune identity
broker ([abraunegg usage.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/usage.md)).

- abraunegg's docs say device-code flow is not allowed for personal Microsoft accounts unless
  Microsoft authorises the app. This is a single-project claim with no Microsoft source
  found; it is unverified and is what gate G5 tests.
- rclone and abraunegg both ship a default client ID and let users supply their own
  ([rclone OneDrive docs](https://rclone.org/onedrive/),
  [application-security.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/application-security.md)).
  A shared public client ID cannot be secret; if Microsoft or a tenant blocks it, every user
  breaks at once.
- Refresh tokens last 90 days and replace themselves on every use; revocation (password
  reset, admin revoke) must be handled by sending the user back to interactive sign-in
  ([Refresh tokens](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens)).
- `Files.ReadWrite.All` is enough to sync any drive once its ID is known; `Sites.Read.All`
  is only needed for site search and followed sites
  ([driveItem delta](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0),
  [site search](https://learn.microsoft.com/en-us/graph/api/site-search?view=graph-rest-1.0)).
- On Omarchy, gnome-keyring owns `org.freedesktop.secrets` (research note
  `file_manager_integration.md`, section 5, local inspection).
- Device-compliance policy is satisfied on Linux through the Microsoft identity broker
  ([abraunegg config options](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/application-config-options.md)).

The Entra pages on loopback redirect and PKCE rules were not read; registration details are
unverified.

## Decision

We register our own Microsoft Entra application as a public client that accepts personal
and work or school accounts, with authority `common`. Its client ID is compiled into the
binaries as a default and can be overridden in `config.toml`.

Interactive sign-in uses the OAuth 2.0 authorization-code flow with PKCE in the user's
system browser. The daemon listens on a loopback redirect `http://localhost:<port>`, where
the port is chosen at random per sign-in. We never use an embedded web view.

`mydrive login --headless` prints the sign-in URL. The user opens it on any device, signs in,
and pastes the URL the browser was redirected to back into the CLI; the daemon extracts the
code and completes the exchange. Device-code flow is offered only if gate G5 shows it works
for personal accounts; until then it is not offered.

The baseline scopes are `Files.ReadWrite.All offline_access User.Read`. `Sites.Read.All` is
requested incrementally, only when the user opens site search (ADR-0015).

Tokens are stored in the Secret Service over D-Bus, one entry per account, and never in plain
text on disk. If no Secret Service is available, the daemon refuses to sign in and
`mydrive doctor` explains how to provide one.

When a refresh fails, the account enters a "needs sign-in" state that is surfaced through the
CLI, tray and notifications. That account's mounts stop syncing; other accounts are not
affected. "Needs sign-in" is an account state, not a value of the per-item sync axis.

Intune identity-broker sign-in is a planned later addition and is not part of this decision.

## Alternatives considered

**Embedded web view.** onedriver's WebKit window rendered blank and broke on Microsoft
changes; it also adds a large toolkit dependency to the daemon. Rejected.

**Device code as the primary flow.** Reportedly unavailable for personal accounts
(unverified) and increasingly blocked by Conditional Access policies (background knowledge,
unverified). Kept only as an optional headless flow behind G5.

**Shipping another project's client ID.** Ties our users to a registration we do not control
and makes its owner responsible for our traffic under the API terms. Rejected.

**Token file on disk.** Simple and works headless, but leaves long-lived refresh tokens
readable by any process running as the user and by backups. Rejected.

## Consequences

- We own the app registration: its publisher details, redirect URIs and privacy statement
  are our responsibility. Creating it is an outward-facing action that needs the owner's
  approval (ADR-0018).
- Headless and server machines without a Secret Service cannot sign in until one is
  provided.
- Each account's failure is isolated, which matches the mount being the unit of sync
  (ADR-0007).
- Open concern: the research suggested an encrypted-file fallback for headless sessions
  where no keyring collection is unlocked. The decision refuses instead, so a headless user
  must run a Secret Service provider. Whether Omarchy's SDDM login unlocks gnome-keyring
  automatically was not checked.

## Rules for implementers

- **R1.** The authorization request always carries a PKCE `code_challenge` with method `S256`,
  and the token request carries the matching `code_verifier`.
- **R2.** The loopback listener binds to the loopback interface only, on a random port, accepts
  exactly one redirect whose `state` matches, then closes.
- **R3.** No code path opens an embedded web view.
- **R4.** The client ID is read from `config.toml` when set, else the compiled-in default.
- **R5.** The initial sign-in requests exactly `Files.ReadWrite.All offline_access User.Read`.
  `Sites.Read.All` is requested only from the site-search flow.
- **R6.** Tokens are written only to the Secret Service. No token, code or verifier is written
  to disk, logs or IPC responses.
- **R7.** With no Secret Service available, sign-in fails with an error that names
  `mydrive doctor`, and nothing is persisted.
- **R8.** A refresh token is replaced by the new one returned on every refresh.
- **R9.** A failed refresh puts only that account into "needs sign-in"; its mounts stop issuing
  Graph requests, and other accounts' mounts keep syncing.
- **R10.** `mydrive login --headless` completes sign-in from a pasted redirect URL, and rejects a
  URL whose `state` does not match.

## Revisit when

- Gate G5 reports whether device-code flow works for personal accounts.
- Microsoft or a tenant blocks our client ID, or Entra changes loopback redirect rules.
- Intune identity-broker sign-in is scheduled.
- Users report headless setups where no Secret Service can reasonably run.
