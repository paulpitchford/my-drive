# Gate G1: `Range` on authenticated `/content` requests

## Status

## Question

Does `Range` work on authenticated `/content` requests, for personal and for work
accounts (open question Q1)? Also recorded, because the same requests answer them:

- whether content responses carry an `ETag` that matches the item's eTag, so a ranged read
  can be tied to a version (Q33, F03 new question 3);
- optionally, whether the identity platform accepts a loopback redirect to `127.0.0.1`
  rather than `localhost` (Q30), if the owner runs the optional step below.

## Method

The program is `crates/mydrive-graph/examples/g1_range.rs`. In order, it:

1. Signs in with the paste flow (F01 headless variant), requesting only
   `Files.Read offline_access openid`. `openid` grants no access to Graph or to files; it
   makes the ID token name the tenant (lead's ruling of 2026-11-15 in WP-011). The
   registration lists `Files.ReadWrite.All`; the identity platform lets a user consent to
   `Files.Read` without it being listed. If the service refuses that scope, the report
   says so and the program stops; the scope is not widened.
2. Reads the `tid` claim of the ID token (for display only, signature not checked), maps
   Microsoft's public consumer tenant `9188040d-6c67-4c5b-b112-36a304b66dad` to
   "personal" and any other tenant to "work", prints the kind and the tenant ID on
   standard error, and sends nothing to Graph until the owner types `yes`.
3. Looks up the drive with `GET /me/drive`, pages its delta until it meets a file of at
   least `--min-size` bytes (default 5 MiB, above the 4 MiB that F03 fetches whole), and
   reads that item's metadata.
4. Picks a range of `--range-len` bytes (default 64 KiB) starting at half the file, at most
   1 MiB in, on a 4 KiB boundary.
5. Reads the file without `Range`, following redirects, up to the end of that range: the
   **reference** bytes.
6. Requests the range three ways:
   - **Way 1**, following the redirect by hand: `/content` with the bearer token and
     `Range`; a redirect is followed with `Range` and without the bearer token, as the
     product does (ADR-0011 R10).
   - **Way 2**, with the bearer token and redirects disabled: one request to `/content`,
     reported as it comes.
   - **Way 3**, with a header that opts into the post-April-2027 behaviour: **not tried: no
     header documented.** On 2026-11-15 the download documentation listed only
     `Authorization` and `if-none-match` as request headers, and MC1492958 (read through a
     mirror) describes a tenant control that administrators use to opt application IDs in
     for testing, not a request header.
7. For each response it reports the status, `Content-Range`, `Content-Length`,
   `Accept-Ranges`, `Content-Type`, `Content-Encoding`, `Transfer-Encoding`, `Retry-After`,
   whether an `ETag` is present and equal to the item's eTag, whether a `Location` is
   present and points at the Graph origin or another origin, error codes, and byte counts;
   and whether each way's range bytes equal the reference bytes.

Every request to Graph and to a download host is a `GET`. The report, on standard output,
holds no token, no pre-authenticated URL, no drive or item ID, no file name, no tenant ID
and no other account identifier; it records only the kind of account. The sign-in address,
the confirmation prompt and any error description from the identity platform appear on
standard error only and are not part of the report. Tokens are held in memory for the
length of the run and never stored.

## How to run it (owner)

On the build machine, from a checkout of this branch, signed in to nothing beforehand.
The program never needs a password typed into the terminal; the sign-in happens in a
browser.

1. `mise install` (once), then
   `mise exec -- cargo build -p mydrive-graph --example g1_range`.
2. Choose a test file: the program uses the first file of at least 5 MiB that the drive's
   delta lists. It only reads. If the drive has no such file, upload one through the
   OneDrive website first, or pass a smaller `--min-size` (keep it above 4194304).
3. Run, keeping the report separate from the prompts:

   ```sh
   mise exec -- cargo run -q -p mydrive-graph --example g1_range > g1-personal.md
   ```

4. Standard error shows a sign-in address. Open it in a browser (any device), sign in
   with the **personal** account, and consent to "read your files" and "maintain access".
   The browser ends on a blank page (the native-client page). Copy its whole address from
   the address bar and paste it at the prompt.
5. The program prints the account kind and tenant ID. Check that it says
   `personal account, tenant 9188040d-6c67-4c5b-b112-36a304b66dad`. Type `yes` only if it
   does. Anything else stops the run before any request reaches Graph.
6. When it finishes, read `g1-personal.md`. Check it holds no name, address, file name or
   ID before copying anything from it. Paste its contents under "Observations: personal
   account" below, with any notes.
7. For a work account: repeat steps 3 to 6 with `> g1-work.md`, signing in with a work or
   school account of a tenant the owner administers or is a member of. Check at step 5
   that the kind is `work` and the tenant ID is the one expected; type anything but `yes`
   if it names a tenant where the owner is only a guest. If no tenant is available, write
   "pending: no tenant available" under the work-account heading.
8. Optional, for Q30: run once more with
   `--redirect-uri http://127.0.0.1:53682`. If the identity platform refuses the redirect
   URI, the browser shows its error before sign-in (record the `AADSTS` code it shows). If
   it accepts it, the browser ends on a "cannot be reached" page whose address holds the
   code; paste that address. Record which happened under "Observations: Q30". Press
   Ctrl-C at the confirmation prompt if the range run itself is not wanted again.
9. Delete the report files when their contents are in this document. Sign out is not
   needed: nothing was stored. To withdraw the consent, use the account's "apps and
   services" page.

The program exits 0 when it reached the range requests, 1 when it stopped earlier (the
report says why), and 2 for a bad command line. `--help` lists the options.

## Conclusion

*Pending.* How the report's summary lines are to be read:

| Observation | Meaning |
|---|---|
| Way 1 ends in `206` on another origin, bytes match the reference | Today's documented path works: ranged reads through the pre-authenticated URL |
| Way 2 answers `302` | `/content` itself does not serve content yet for this account; the answer for after 2027-04-01 is still unknown |
| Way 2 answers `206` with bytes that match | `Range` is honoured on authenticated `/content` directly: ranged hydration survives the retirement of pre-authenticated URLs |
| Way 2 answers `200` | Authenticated `/content` serves content but ignores `Range`: the client must treat the drive as range-ignoring (F03 note 9) |
| Any way's bytes differ from the reference | A serious finding: stop and report to the lead before anything else |
| The ETag line says "equal to the item's eTag" | Ranged responses can be checked against the expected version (Q33) |

## What it means for the ADRs

*Pending.* ADR-0005 keeps ranged hydration provisional, with whole-file hydration as the
fallback, and ADR-0011 R10 and R11 already require the client to handle `302`, `200` and
`206` per response, until this gate is answered. The lead changes the ADRs from the
findings; this document does not.

## What could not be verified

- Nothing has been run against the real service yet.
- Whether an opt-in header exists: none is documented, so way 3 was not tried. If one is
  documented later, the experiment should be repeated with it.
- Whether personal accounts are in scope of MC1492958 at all; the message does not say.
- In the simulator tests, the identity platform is a fake in the test code, and the
  `GET /me/drive` lookup is tested only on fixed input and for its failure path, because
  the simulator has no `/me` routes until WP-023 merges.
