## Findings

### 1. The design the ADR chose

The ADR's status is "**Proposed**", not accepted ([ADR] L3). It describes itself as "the
intended architecture and safety invariants ... It distinguishes architectural decisions from
implementation mechanisms that still require prototype validation" ([ADR] L10).

**Where content is stored; mount over the sync directory or separate.** The FUSE mount sits
**over the existing sync directory**, and hydrated content lives physically underneath it:

- "FUSE is mounted over the existing configured `sync_dir`." ([ADR] §2.3, L65)
- "Hydrated database items are backed by real physical content in the existing `sync_dir`."
  ([ADR] §2.6, L68)
- "INV-006 — `sync_dir` remains the user-facing path. No second user-visible OneDrive
  directory is introduced." ([ADR] L844–845)
- The engine reaches the covered physical tree through "a directory handle/file descriptor to
  the physical `sync_dir`", retained before the mount, plus `openat()`/`renameat()`-style
  calls. The ADR labels this "an **implemented experimental mechanism**, not yet a proven
  production architecture" ([ADR] §11.1, L490–500).
- The scaffold commit says the same: "mounting directly over the configured sync_dir while
  retaining access to the underlying physical filesystem ... without introducing a separate
  backing directory" ([C-overlay]).

**Placeholders.** There are none on disk. The item database is the namespace:

- "The item database is the authoritative namespace presented by FUSE." ([ADR] L30)
- "Cloud-only database items are visible without physical placeholder files." ([ADR] §2.5, L67)
- With FUSE absent, "cloud-only items are not locally visible as filesystem entries. They have
  not been deleted." ([ADR] §5, L236)
- Stable states are "equivalent to `CLOUD_ONLY` / `HYDRATED`". The exact representation is
  left open ("A boolean may be sufficient for stable state"), and transient states such as
  "hydration in progress" and "local content dirty / awaiting upload" are kept separate
  ([ADR] §6, L256–274).

**What triggers hydration; open vs read; whole file vs ranges.** The ADR deliberately leaves
the trigger open:

- "A content-requiring operation against a cloud-only item requests hydration." ([ADR] §9, L376)
- Enumeration, lookup, stat and existence checks "should normally be satisfiable from DB/FUSE
  metadata", and "The exact FUSE callback-to-hydration boundary must be tested against real
  file managers and applications." ([ADR] §9.1, L384–391)
- Open decision 12: "What exact operation constitutes content demand" ([ADR] L1028).
- The hydration diagram starts at "open/read file", and the title of that diagram is
  "Cloud-only open and hydration" ([PUML] hydration-sequence; [ADR] L378).
- It is **whole-file**: "Engine -> Disk : safe temporary download", then "validate completed
  content", then "atomically materialise backing file", then "commit HYDRATED" ([PUML]
  hydration-sequence). §9.3 requires "avoid exposing incomplete content as complete" and
  "materialise final backing content atomically where possible" ([ADR] L407, L412).
- The ADR does not mention ranges, sparse files or partial hydration anywhere (checked by
  search across all four revisions). The maintainer later called ranged reads "later-stage
  behaviour" ([D3891-pause]).
- Hydration must reuse the existing download path: "FUSE must not implement an independent
  Microsoft Graph downloader." ([ADR] L416; INV-010, INV-022)

**How state is persisted.** "The database gains explicit stable hydration state for applicable
file items." ([ADR] §2.2, L64) The schema is open decision 1. Which transient operations
survive a restart is open decision 3 ([ADR] L1017–1019). The hydrated state is committed "only
after valid physical content has been safely materialised" ([ADR] §2.14, L76; INV-016).

**Writes and uploads.** FUSE writes go to the physical file. The existing inotify monitor on
the physical tree is meant to detect them, and the existing engine uploads:

- "No special FUSE upload engine." ([ADR] §10, L450)
- "FUSE mediates the filesystem operation; the physical backing content changes; the existing
  local-change machinery observes the physical change; the existing sync engine performs the
  upload/update." ([ADR] L452)
- §10.1 is headed "This must be proven, not assumed". It lists open questions: where watches
  attach, whether FUSE-routed writes raise events on the physical tree, editor atomic saves,
  and "whether hydration writes themselves generate events that must be
  suppressed/recognised" ([ADR] L454–470).
- `on_demand` requires `--monitor`: "A single-run `--sync` with `on_demand = "true"` is
  unsupported and must be rejected" ([ADR] §4, L110; INV-002).

**Pinning and freeing space.**

- "Pin/`always_local` is policy, not hydration state" ([ADR] §6.3, L305–309). Its syntax and
  how it interacts with `sync_list` "require a separate decision" ([ADR] §16, L643–653).
- Dehydration is allowed only when content can be removed "without data loss". A file must not
  be auto-dehydrated when it is "locally modified or unsynchronised", "uploading", "subject to
  unresolved conflict", "required by `always_local`", or "in any ambiguous state" ([ADR] §15,
  L590–601).
- "User deletion and dehydration are different operations and must never be inferred from
  physical absence alone." ([ADR] §2.17, L79; §14)
- "Automatic expiry must be **opt-in and disabled by default**." ([ADR] L623)

**Thumbnailers and indexers.** These are a mandatory part of the hydration milestone (added in
the 2026-10-12 revision):

- "Known indexers and thumbnail generators must **not automatically hydrate cloud-only
  content**. This protection is a required part of the demand-hydration milestone"
  ([ADR] §9.4, L422).
- The mechanism is a "default-enabled, conservative process-identity blocklist" using "the FUSE
  request-context PID and, where available, `/proc/<pid>/exe` and `/proc/<pid>/comm`". The
  candidates listed are `baloo_file`, `baloo_file_extractor`, `tracker-miner-fs-3`,
  `localsearch-3` and `tumblerd` ([ADR] L424–427).
- A blocked request returns "a defined filesystem error", with `EACCES` or `EPERM` to be chosen
  "only after observing retry and user-interface behaviour". Unknown processes hydrate
  normally. `kioworker` must not be blocked indiscriminately ([ADR] L428–431).

**Offline and daemon-down.**

- Clean shutdown unmounts FUSE, and "physical hydrated content in `sync_dir` becomes directly
  visible" ([ADR] §2.18, L80). With the client stopped, the user sees only the hydrated files
  ([PUML] shutdown-visibility: "FUSE absent / client stopped" → "report.pdf only").
- "A process crash must not make hydrated data dependent on FUSE." (INV-017, [ADR] L877)
- Edits made while the client is stopped are kept and reconciled; the database's authority
  "does not authorise destruction or overwriting of contradictory unsynchronised physical
  content" ([ADR] L104, §12).
- On network failure, hydration must "return an appropriate filesystem error when hydration
  cannot complete" ([ADR] L414). No errno or timeout is fixed.
- Stale and failed mounts: "Unmount must be attempted and verified before the helper is
  terminated ... Stale FUSE mounts must be detected at the next startup" ([ADR] §18.1.1, L715).

### 2. Alternatives considered and why they were rejected

**The ADR records no alternatives.** No revision has an "Alternatives considered" section.
fanotify, stub files, a separate backing directory and other mechanisms are never named
(searched across all four revisions, L1–1107). The only rejections it records are of
*internal* options:

- rejecting a second sync engine: "must not create a second implementation of Microsoft Graph
  change processing, downloads, uploads ..." ([ADR] L26);
- rejecting a parallel upload path "without evidence that the existing path cannot be
  retained" (INV-011, [ADR] L860);
- rejecting `on_demand` with `--sync` (INV-002).

Rejections of alternatives do appear in other sources:

- **Stub files (the 2020 attempt).** PR #921 used empty or stub files, without FUSE. The
  maintainer said: "I already have a working prototype ... this does not use FUSE, but empty
  files are used" ([I757 comment](https://github.com/abraunegg/onedrive/issues/757#issuecomment-578294917)).
  Its known issues included new files being "replaced by a 23 byte file", and that editing a
  stub "will fail & crash the application. This is due to ZERO file system capability under
  Linux to set a lock / delay file access whilst the file is being downloaded"
  ([I757 comment](https://github.com/abraunegg/onedrive/issues/757#issuecomment-630544998)).
  The PR was closed "in favour of https://github.com/jstaf/onedriver" on 2021-01-27
  ([PR921](https://github.com/abraunegg/onedrive/pull/921#issuecomment-768533826)).
- **fanotify** was suggested by a user in 2021
  ([I757 comment](https://github.com/abraunegg/onedrive/issues/757#issuecomment-812566395)).
  The maintainer never answered it.
- **A separate hidden backing directory.** The contributor fork built this first and then
  dropped it: "The first version kept hydrated files in `<confdir>/ondemand/backing`, with the
  mount at `sync_dir`. That hid every downloaded file whenever the client was stopped. After
  reading ADR §11 we moved to the physical `sync_dir`." ([FORK] §6) The maintainer welcomed
  the move: "I appreciate that you have now moved the implementation onto the physical
  `sync_dir` model" ([D3891-pause]).

**Inference.** Upstream's choice of overmounting appears to be driven by two goals: keep the
existing D sync engine and its inotify monitor unchanged ("Do not replace working
synchronisation paths. Change when content is materialised." [ADR] L317), and keep hydrated
files reachable with the client stopped. It is not the result of a written comparison of
mechanisms.

### 3. Problems, limitations and open questions on record

From the ADR:

- 23 numbered open decisions ([ADR] §26, L1017–1039). The ones that matter most to us:
  - 4 and 5: how FUSE learns of DB changes, and the kernel cache policy;
  - 7: "Does existing inotify reliably observe all FUSE-routed mutation patterns?";
  - 9 to 11: serialising concurrent hydrations, and crash-safe commit ordering for hydration
    and dehydration;
  - 12 and 13: what counts as content demand, the errno for blocked readers "without causing
    retry loops", and "PID reuse, and `/proc` failures";
  - 20: "How should FUSE behave if the DB is temporarily unavailable or inconsistent?";
  - 22: "How are failed unmount and stale mount state verified and safely recovered?";
  - 23: "What bounded lookup and cache-invalidation strategy remains efficient for 100K+
    items?"
- Scale: "The chosen mechanism must be evaluated for very large namespaces. On-demand support
  should not turn every filesystem operation into an unnecessarily expensive full database
  traversal." ([ADR] L368)
- The FUSE layer is not production-ready. "Their callback signatures, struct layouts and
  lifecycle must be validated against the supported FUSE3 ABI". The scaffold "still requires
  runtime proof of callback ABI correctness, errno mapping, file-handle and threading
  behaviour, verified readiness, clean unmount and stale-mount recovery" ([ADR] §22,
  L808–823). An earlier revision says plainly: "Recovered groundwork contains D bindings with
  FUSE2-style callback signatures while the build configuration targets FUSE3" (revision
  `e8cda6ea`).
- "Cloud-only absence is never local deletion. This is a release-blocking invariant."
  ([ADR] §13, L542)
- "This feature has a high data-loss impact if state transitions are wrong." ([ADR] §25, L954)

From the PR, its commits and comments:

- The PR title carries "(DO NOT USE)" (renamed 2026-10-03, [PR] events). The maintainer told a
  reviewer: "This PR is just my development branch for a number of things in my local
  environment. Please do not use or assume this is introducing any capability."
  ([PR](https://github.com/abraunegg/onedrive/pull/3600#discussion_r2728972404), 2026-01-26)
- The scaffold is a pure passthrough: "This establishes the physical-overlay architecture
  only. Cloud-only namespace presentation, hydration state, pinning, dehydration and related
  on-demand behaviour are not implemented by this change." ([C-overlay]) `src/ondemand.d`
  says: "This module intentionally contains no OneDrive/Graph/database/hydration logic."
- A code-scanning review found libfuse's `-d` debug flag hard-coded, which "dumps every path
  and filesystem operation performed against the user's sync directory into stderr/journal
  logs" ([PR](https://github.com/abraunegg/onedrive/pull/3600#discussion_r4300063811)). The
  maintainer fixed it in the last commit, 2026-10-24
  ([PR](https://github.com/abraunegg/onedrive/pull/3600#discussion_r4368419471)).
- All other PR comments are from bots (spelling checks and E2E results).

From the maintainer in discussion #3891 ([D3891-pause], 2026-10-04):

- A gap in the ADR: "A delete, rename or move of an online-only item can be purely a
  namespace operation and may not touch the physical filesystem at all, so there is no
  physical inotify event to observe." He expects the design to become "hybrid rather than 'all
  inotify' or 'all synthetic FUSE events'".
- The engine is not ready for this. He notes the fork's hydration "has to bypass
  `SyncEngine.downloadFileItem` and use a separate lower-level download path because the
  existing engine state is not thread-safe", and calls that "a sign that the engine interface
  itself may need work".
- "the ADR currently needs an update around `--monitor`" (since fixed in the 2026-10-12
  revision).

From the contributor fork, which has run daily on one Personal drive since 2026-10-02 ([FORK]):

- Ten hydrations in flight blocked the whole mount: "With the libfuse default of 10, ten slow
  downloads blocked every other request." (§4)
- "Renaming an online-only file hydrates it first." (§10, §20, "a known gap")
- The file-manager refresh gap (§12): "when the engine changes the physical tree, an inotify
  watcher on the mount (Nautilus through GIO) sees nothing". `fuse_lowlevel_notify_inval_entry`,
  `notify_delete`, `notify_inval_inode` and `fuse_invalidate_path` were tried on kernel 7.0
  with libfuse 3.14: "None produced inotify events on the mount." Their fix is a "replay
  thread" that makes a matching no-op syscall on the mount for each engine change.
- File managers sniff content: "In the first daily use this downloaded files nobody had asked
  for. The caller cannot tell a sniff from a copy: Nautilus does both on the same worker
  threads." (§10)
- Version mixing: "If the database item changes between two reads, that read and all later
  reads on the handle fail with EIO ... Versions are never mixed within a handle." (§10)
- Thumbnailer PIDs: "We have not verified pid resolution for thumbnailers inside GNOME's bwrap
  sandbox." (§13)
- systemd units run "without sandboxing, because a private mount namespace would hide the
  mount" (§15).
- `getcwd()` gotcha: "`getcwd()` still returns the `sync_dir` string, though, and
  `chdir(getcwd())` lands on the mount", so every absolute path built from `sync_dir` had to be
  audited (§6).
- Range support: "Graph's `downloadUrl` honoured `Range` on Personal. We have not checked it on
  Business." (§10)
- Not tested: "OneDrive Business, SharePoint libraries, shared folders and files, FreeBSD,
  very large namespaces, disk-full during hydration." (§19)

**Inference on "reason for stopping".** None of these problems is described by the
maintainer as a blocker to the FUSE approach. The one item he ties to a pause is the
engine's thread-safety and interface, and that leads into finding 4.

### 4. Why the work is on hold

### 5. Comparison with ADR-0005

**Where we agree:**

| Topic | Upstream ADR-001 | ADR-0005 / ours |
|---|---|---|
| Mechanism | FUSE3, unprivileged | FUSE (`fuser`), unprivileged |
| Namespace source | Item DB is authoritative ([ADR] L30) | SQLite store is the source of truth (ADR-0006) |
| No hydration on metadata | Enumeration, lookup and stat must not hydrate (INV-014) | R1: `readdir`, `lookup`, `getattr`, `open`, xattr never hydrate |
| Pin vs residency | Pin is policy, not hydration state (§6.3) | Separate pin and hydration axes (ADR-0008) |
| Free vs delete | Distinct operations, never inferred from absence (§14) | Dehydrate refused unless `InSync` and not pinned; deletes are explicit VFS events |
| Dirty data | "Unsynchronised local data wins over reclamation" (INV-012) | ADR-0012 durable dirty mark; never dehydrated or overwritten |
| Indexers | Default-on PID deny list via `/proc/<pid>/comm` and `exe` (§9.4) | ADR-0013 deny list, plus a circuit breaker and thumbnail seeding |
| Failure | Return a filesystem error when hydration fails (§9.3) | `EIO` within a bounded time, never zeros (R4) |
| Stale mounts | Detect at startup and recover (§18.1.1) | Daemon unmounts stale mounts on start (overview) |

**Where we differ:**

| Topic | Upstream ADR-001 | ADR-0005 / ours |
|---|---|---|
| Layout | FUSE **overmounts** `sync_dir`; hydrated files physically under it | FUSE at the mount point; content in a **separate hidden backing directory** |
| Daemon down | Hydrated files visible and editable in `sync_dir`; cloud-only items vanish | Mount point is an empty directory; nothing is visible |
| Placeholders | None on disk; cloud-only items exist only in the DB | Sparse backing files with `st_size` = cloud size |
| Hydration unit | Whole file, staged, validated, then atomic rename | Byte ranges plus read-ahead into sparse files; whole-file only if G1 fails |
| Trigger | "content-requiring operation", left open (§9.1, decision 12) | `read` only, including mmap faults |
| Local change detection | Existing inotify on the physical tree, plus FUSE signals for cloud-only operations (hybrid) | VFS reports write and namespace events to the engine directly (overview diagram) |
| Engine | Reuse the existing D engine unchanged; FUSE must not download | New engine designed for this; the VFS asks the engine through `core` traits |
| Mode | Requires `--monitor` | Daemon is always running |
| Errno | Undecided (`EACCES`/`EPERM`/other) | `EIO` |

**Inference.** Upstream's two main reasons for overmounting do not apply to us. They want to
keep a legacy engine and inotify monitor working, and to keep hydrated files usable when the
client is stopped. We have no legacy engine. We chose principle 2 ("fail loudly, never
silently") over visibility while the daemon is down. Nothing in the sources argues that a
separate backing directory is unsafe. The fork dropped it for the visibility cost, not for a
correctness failure.

**Pitfalls they hit that ADR-0005 does not yet cover** (most important first):

1. **Mixing versions in partially hydrated files.** The fork fails a handle's reads with `EIO`
   once the item's content version changes between reads, so that "Versions are never mixed
   within a handle" ([FORK] §10). It also checks that the `Content-Range` total equals the
   recorded size. ADR-0005 hydrates by range into a sparse file and records extents
   (R5–R6), but it does not say what happens to hydrated extents when a remote change
   arrives. Nor does it say how a ranged response is tied to the version whose extents are
   already on disk. Without that, a partial file could end up with bytes from two versions,
   which is silent corruption (principle 1). Upstream avoids this entirely by hydrating whole
   files atomically.
2. **File managers do not refresh after daemon-side changes.** The fork found that
   changes the engine makes behind the mount (remote updates, hydration, frees) produce no
   inotify events on the FUSE mount, and that none of the four libfuse invalidation calls they
   tried fixed this on kernel 7.0 ([FORK] §12). Our daemon writes to the backing directory and
   the store, never through the mount, so this applies to us in full. Adapters can use the IPC
   change stream (ADR-0009), but principle 4 says plain file managers without an adapter must
   work too. ADR-0005 needs a stated mechanism: replay through the mount, or an accepted
   limitation with a test.
3. **Blocking hydration starves the mount.** "ten slow downloads blocked every other request"
   ([FORK] §4). ADR-0005 does not say how the VFS dispatches requests. If a read waits up to
   30 s for the network (R4), that wait must not block `lookup`, `getattr` or reads of local
   data on other files. **Inference, unverified:** `fuser` handles requests on a single
   session loop unless the filesystem hands work off, so this needs a rule.
4. **Namespace operations on placeholders.** The fork's rename of an online-only file
   hydrates it, which it calls a gap. The maintainer noted that a delete, rename or move of an
   online-only item may touch no physical file ([D3891-pause]). ADR-0005 R1 lists `readdir`,
   `lookup`, `getattr`, `open` and xattr calls, but not `rename`, `unlink`, `rmdir` or
   `setattr` (other than size changes). It should say they never hydrate. A rename of a
   placeholder would then be a server-side move.
5. **The cost of the backing directory should be written down.** The fork's experience
   ("hid every downloaded file whenever the client was stopped") is the cost we have chosen.
   ADR-0005 states the benefit (no zeros) but not this cost: pinned "always keep on this
   device" files are unreachable whenever the daemon is not running, for example if it fails
   to start or the user stops it. The consequence should be stated, and `mydrive doctor` and
   the journey docs should cover "daemon will not start, I need my pinned file".
6. **systemd sandboxing hides the mount.** The fork's user units run "without sandboxing,
   because a private mount namespace would hide the mount" ([FORK] §15). ADR-0016 does not
   mention unit hardening. A rule is needed: no `PrivateMounts=`, `ProtectHome=`,
   `PrivateTmp=` or other mount-namespace options in the user unit.
7. **Stale mounts can be dead, hung or live.** The fork probes a matching mount with `statfs`
   in a child process under a timeout. It refuses to start if the mount answers (another
   instance is running) or times out (hung), and lazily unmounts only on `ENOTCONN`
   ([FORK] §6). Our overview just says "unmounts stale mounts on start". Unmounting a live
   mount owned by a second daemon, or hanging on a stuck one, are both possible.
8. **A lost backing directory is not a mass delete.** The fork refuses to start if the store
   says files are hydrated but none are present ("catches an unmounted disk or an emptied
   `sync_dir`"). It also totals queued deletes against a big-delete threshold ([FORK] §6).
   ADR-0006's recovery scan should say that a backing file missing for a `Full` or `Partial`
   item becomes `Placeholder` (or `Error` if it was dirty), never a remote delete. **Inference:**
   our design is less exposed than upstream's, because local deletes come only from VFS
   events, but the recovery scan is the one place that compares disk to the store.
9. **Remote change to an open file.** The fork defers a newer remote version while the file is
   open and applies it on last close, "Behaviour that follows the Windows client" ([FORK]
   §11). ADR-0012 covers dirty files but not a clean file that is open for reading when its
   backing content would be replaced.
10. **Content sniffing by file managers.** "Nautilus does both [sniff and copy] on the same
    worker threads" ([FORK] §10). ADR-0013's deny list does not cover the file manager itself,
    and blocking it would break copies. Our ranged hydration limits a sniff to the requested
    range plus read-ahead, which is a natural advantage over upstream's whole-file design.
    The read-ahead size should be chosen with sniffing in mind (the fork saw "32 KB content
    sniffs").

Things ADR-0005 already covers that upstream left open: the errno (`EIO`), a bounded
timeout, `st_blocks` for local bytes (the fork does the same, [FORK] §11), mmap via `read`,
and rejecting FUSE passthrough and io_uring because they need root.

## Conclusion for ADR-0005

**Recommendation to the lead: pass with changes.**

- The gate asked whether abraunegg's FUSE work found a reason to doubt our approach. It did
  not.
  - Upstream's ADR is a *Proposed* design for overmounting `sync_dir`, with no comparison of
    alternatives.
  - The only code is a passthrough scaffold.
  - The pause was for competing priorities: "The 100K-object memory work is currently more
    important". It was not for a FUSE failure.
- Upstream and the fork confirm the parts we share: a DB-authoritative namespace, no hydration
  on metadata, pin kept apart from residency, free kept apart from delete, and a PID-based
  indexer guard.
- Upstream chose overmounting to keep a legacy engine and inotify monitor, and to keep files
  visible when the client is stopped. Neither reason outweighs principle 2 for us. We suggest
  ADR-0005 keep the separate backing directory.

Changes we recommend before M2 work starts (the lead decides):

1. Add version safety for partial hydration (pitfall 1).
   - Hydrated extents are tied to a content version (eTag/cTag or hash).
   - A remote content change invalidates them.
   - Ranged responses are checked against that version and against the recorded size.
   - An open handle never sees bytes from two versions; it gets `EIO` instead.
2. State how the VFS dispatches requests (pitfall 3): network waits must not block requests
   for other files or for local data. Add a test with N concurrent slow hydrations.
3. Extend R1 to `rename`, `unlink`, `rmdir`, `link` and non-size `setattr` on placeholders
   (pitfall 4).
4. Add a decision, or a recorded limitation with a test, on how file managers without an
   adapter learn of changes the daemon makes behind the mount (pitfall 2). Cross-reference
   ADR-0014.
5. Record the consequence that pinned content is unreachable while the daemon is down
   (pitfall 5).
6. Handle remote changes to files that are open but clean (pitfall 9), here or in ADR-0012.
7. In other ADRs:
   - ADR-0016: forbid mount-namespace sandboxing in the user unit (pitfall 6).
   - Overview or ADR-0005: classify stale mounts as dead, hung or live before unmounting
     (pitfall 7).
   - ADR-0006: a missing backing file in the recovery scan is never a delete (pitfall 8).
