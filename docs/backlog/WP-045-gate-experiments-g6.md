# WP-045: Gate experiment G6, write-side behaviour

- **Status:** ready
- **Milestone:** M1
- **Wave:** 7
- **Depends on:** WP-008, WP-009
- **Gates:** answers G6
- **Owned paths:** `crates/mydrive-graph/examples/g6_*.rs`, `crates/mydrive-graph/examples/g6/**`,
  `crates/mydrive-graph/tests/g6_*.rs`, `docs/gates/G6.md`
- **ADRs:** ADR-0010, ADR-0011, ADR-0012, ADR-0015, ADR-0017
- **Flows / journeys:** F04, F07

## Goal

Measure, on a real account, the write-side behaviours the upload and conflict design rests
on and the simulator can only guess at. Above all: when SharePoint rewrites an uploaded file,
does the upload response already carry the rewritten hash and eTag, or do they arrive only
in a later delta, and how much later (open question Q42).

## In scope

An example program, run by the owner, that works only inside a scratch folder it creates,
and records for a personal drive and for a document library:

- **Rewriting.** Upload small `.docx`, `.xlsx`, `.pptx`, `.pdf` and `.txt` files by upload
  session. Record the hash, size and eTag in the upload response, in an immediate read of
  the item, and in reads and delta pages at 1, 2, 5, 15 and 60 seconds: when each value
  changes, and whether `fileSystemInfo` times and `lastModifiedBy` change with it.
- **`If-Match`.** On simple `PUT .../content`, on an upload session, on `PATCH` and on
  `DELETE`: the status and error code for a stale eTag, for a cTag, and for a current eTag;
  the status of a successful replace (200 or 201).
- **Conflict behaviour.** The default and each `@microsoft.graph.conflictBehavior` value for
  upload by name and create folder, on a name differing only in case; the status and code.
  Whether `PATCH` (rename onto a taken name) honours `replace` is tested only against items
  the program created.
- **Names.** Whether `#` and `%` in a name are refused, and with what error.
- **IDs and times.** Item-ID casing across the upload response, a read and delta; whether
  supplied `fileSystemInfo` times are kept, and at what precision; whether a rename changes
  `lastModifiedDateTime`.
- **Folder delete.** How delta reports the deletion of a folder with children.
- `docs/gates/G6.md`: method, date, account types, observations (redacted), conclusions, and
  what each means for ADR-0012, the simulator's switches and Q42.

## Out of scope

- Anything outside the scratch folder. Change notifications (deferred). Quota and lock
  behaviour. Any change to ADRs or to the simulator (the lead does that from the findings).

## Acceptance criteria

- AC1: The program creates one scratch folder with a fixed, recognisable name prefix and a
  random suffix, and every later request addresses an item by an ID the program itself
  received when creating it in this run. A test against `mydrive-graph-sim` records every
  request and fails if any write targets an item the run did not create.
- AC2: It never deletes, renames, moves or overwrites an item it did not create, and never
  empties the recycle bin. If the scratch folder name already exists it stops; it does not
  reuse or replace it.
- AC3: It writes nothing without an explicit flag whose name says it writes to a real
  account, prints the drive it will use and what it will do first, and has a dry-run mode
  that makes no request other than reads.
- AC4: It cleans up by deleting only the scratch folder it created, reports if that fails,
  and leaves the folder in place when asked to (for inspection).
- AC5: Output and the gate document contain no token, no pre-authenticated URL, no account
  name, email, tenant, site or drive identifier, and no file content other than the
  program's own generated test data.
- AC6: The observation logic (what is recorded at each step and how changes are detected) is
  tested against the simulator in both rewriting modes, and reports each mode correctly.
- AC7: `docs/gates/G6.md` is filled in from a real run by the owner; any part not run is
  recorded as pending.

## Required tests

- As AC1, AC3 and AC6, in `crates/mydrive-graph/tests/g6_*.rs`, against the simulator only.

## Notes

The owner approved this gate on 2026-11-15, for a scratch folder of their own account and a
scratch document library of their own tenant. The implementer builds and tests against the
simulator and stops there. Running it needs the owner to sign in; the implementer never
signs in to a real account and never runs the program against one.

The Graph client has no write operations yet (WP-025). This example may make its write
requests with the HTTP client directly, using the existing sign-in and token code; it must
not add write operations to the library.

Test data is generated by the program (small valid Office files built from fixed bytes
checked into `examples/g6/`), so no user file is ever read or uploaded.
