Scope note: generic driveItem delta mechanics, upload sessions, throttling numbers, hashes, the April 2027 pre-authenticated URL retirement and the `/me/drive/sharedWithMe` deprecation are covered in `graph_api_and_windows_parity.md` and are not repeated here. gvfs and Insync generalities are in `existing_clients.md`.

Verification note: every bullet under "Cited Findings" comes from a page fetched in this session (Microsoft pages carried `updated_at` stamps between Dec 2025 and Jul 2026). Pages were read through a summarising fetch tool, so quoted strings are as that tool reported them; a few are marked where the tool paraphrased. ## 1. Discovery: enumerating sites, libraries and Teams channel folders

### Takeaway
There is no single "list every library I can reach" call. Every site-level discovery endpoint (`/sites?search=`, `/me/followedSites`) needs `Sites.Read.All` and is work/school only, whereas resolving a pasted link via `/shares/{encoded-url}` and resolving a Teams channel via `filesFolder` work with Files.* scopes alone. A paste-a-URL flow plus a Teams browser is therefore the lowest-privilege discovery UX; site search is an optional extra that costs a broader scope.

### Cited Findings
- `GET /sites?search={query}` requires delegated `Sites.Read.All` (least privileged) or `Sites.ReadWrite.All`; personal Microsoft accounts are "Not supported". — [Graph: Search for sites](https://learn.microsoft.com/en-us/graph/api/site-search?view=graph-rest-1.0)
- Site search is "a free text search that uses multiple properties when retrieving the search results", and "The only property that works for sorting is **createdDateTime**". — [Graph: Search for sites](https://learn.microsoft.com/en-us/graph/api/site-search?view=graph-rest-1.0)
- Site search "doesn't support the Sites.Selected application permission". — [Graph: Search for sites](https://learn.microsoft.com/en-us/graph/api/site-search?view=graph-rest-1.0)
- Site IDs are a three-part composite, e.g. `contoso.sharepoint.com,da60e844-...,712a596e-...` (hostname, site collection GUID, web GUID). — [Graph: Search for sites](https://learn.microsoft.com/en-us/graph/api/site-search?view=graph-rest-1.0)
- `GET /me/followedSites` requires delegated `Sites.Read.All` (higher: `Sites.ReadWrite.All`); it is not supported for personal accounts or for application permissions, and "is accessible only through OneDrive for Business". — [Graph: List followed sites](https://learn.microsoft.com/en-us/graph/api/sites-list-followed?view=graph-rest-1.0)
- Microsoft warns that followedSites "has a known issue and might return incorrect results" (the linked known issue is titled follow/unfollow sites "is not in sync with SharePoint following"). — [Graph: List followed sites](https://learn.microsoft.com/en-us/graph/api/sites-list-followed?view=graph-rest-1.0)
- `GET /teams/{id}/channels/{id}/filesFolder` returns a driveItem whose `parentReference` carries the library `driveId` and `"driveType": "documentLibrary"`. Least-privileged delegated permission is `Files.Read.All`; `Files.Read`, `Files.ReadWrite`, `Files.ReadWrite.All`, `Sites.Read.All`, `Sites.ReadWrite.All` also work. `Group.Read.All`/`Group.ReadWrite.All` are "supported only for backward compatibility". — [Graph: Get filesFolder](https://learn.microsoft.com/en-us/graph/api/channel-get-filesfolder?view=graph-rest-1.0)
- filesFolder: "Some special characters in the channel name will cause this API to return an error." — [Graph: Get filesFolder](https://learn.microsoft.com/en-us/graph/api/channel-get-filesfolder?view=graph-rest-1.0)
- Recently changed (private channels): "After a private channel is migrated, the default file location changes to the root folder, and the `GET /teams/{team-id}/channels/{channel-id}/filesFolder` API returns the root folder's `driveItem`. Newly created private channels (post-migration) no longer create a dedicated folder." For pre-migration private channels "a dedicated folder that matches the channel name may still exist". — [Graph: Get filesFolder](https://learn.microsoft.com/en-us/graph/api/channel-get-filesfolder?view=graph-rest-1.0)
- `GET /shares/{shareIdOrEncodedSharingUrl}` accepts "a properly encoded sharing URL": base64-encode the URL, convert to unpadded base64url (strip `=`, `/`→`_`, `+`→`-`), prefix `u!`. Least-privileged delegated permission is `Files.ReadWrite` (higher: `Files.ReadWrite.All`, `Sites.ReadWrite.All`). `/shares/{id}/driveItem` returns the underlying driveItem; `?$expand=children` lists a shared folder. — [Graph: Access shared items](https://learn.microsoft.com/en-us/graph/api/shares-get?view=graph-rest-1.0)
- `Prefer: redeemSharingLink` grants "the caller durable access to the item" and is "equivalent to the caller navigating to the sharing link the browser (accepting the sharing gesture)"; `redeemSharingLinkIfNecessary` only guarantees access "for the duration of this request" and is meant "to peek at the link's metadata". — [Graph: Access shared items](https://learn.microsoft.com/en-us/graph/api/shares-get?view=graph-rest-1.0)
- "For OneDrive for Business and SharePoint, the Shares API always requires authentication and can't be used to access anonymously shared content without a user context." — [Graph: Access shared items](https://learn.microsoft.com/en-us/graph/api/shares-get?view=graph-rest-1.0)
- The "Shared with me" view grouping "can't be synced from work or school sites" even by Microsoft's client. — [Microsoft Support: Restrictions and limitations in OneDrive and SharePoint](https://support.microsoft.com/en-us/office/restrictions-and-limitations-in-onedrive-and-sharepoint-64883a5d-228e-48f5-b3d2-eb39e07630fa)
- Folders shared by people outside the user's organisation cannot be synced by abraunegg/onedrive; the project attributes this to Graph "not presenting these folders" (tracked as its issue #966). — [abraunegg/onedrive: business-shared-items.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/business-shared-items.md)

### Inferences
- A client that requests only Files.* scopes can still onboard a library in two ways: (a) the user pastes a library/folder URL or sharing link, resolved with `/shares/u!...`/driveItem, then read `parentReference.driveId`; (b) Teams → channel → `filesFolder`. Both yield a `driveId` that can be delta-synced as its own drive. Site search and followed sites should be treated as a progressive-enhancement path gated on `Sites.Read.All` being granted.
- `redeemSharingLink` permanently changes the user's access (it is the same as clicking the link), so a "preview what this URL is" step in an add-library wizard should use `redeemSharingLinkIfNecessary` and only redeem durably when the user confirms.
- Because of the private-channel migration, a client cannot assume that a channel's files live in a same-named subfolder of the team's default library; it must take whatever driveItem (possibly a drive root in a different site) `filesFolder` returns, per channel.
- followedSites is unreliable by Microsoft's own admission, so it should populate suggestions, never be the only route to a site.

### Gaps
- Not verified this session (prior knowledge only; confirm before relying on it): the path-addressing form `GET /sites/{hostname}:/{server-relative-path}`, `GET /sites/{site-id}/drives` (all libraries in a site) and `GET /groups/{group-id}/drive` / `/drives`, `GET /me/joinedTeams`, and the statement that private and shared channels each get their own SharePoint site collection. The filesFolder note above is consistent with the separate-site model but does not state it outright.
- The shares doc says "sharing URL"; whether a plain (non-sharing-link) SharePoint library or folder browser URL is always resolvable through `/shares/u!...` was not confirmed from a primary source.
- Whether `filesFolder` works for shared channels hosted in another tenant with delegated tokens was not investigated.
- No source found that gives a supported way to enumerate "all libraries the user can access" without `Sites.Read.All` (e.g. via the Search API); not investigated.

## 2. Permissions, consent and tenant policy

### Takeaway
Files.ReadWrite.All is enough to sync any library the user can reach once the client knows its drive ID; Sites.Read.All is needed only for site search and followed sites. The real blockers for a third-party client are tenant-side: unmanaged-device Conditional Access policies explicitly cut off app access (browser-only, "no ability to download, print, or sync"), and tenants can refuse consent to the app altogether. The "domain-joined only" sync restriction is documented as an Active Directory, sync-app setting; its effect on Graph clients is not documented.

### Cited Findings
- driveItem delta accepts, for delegated work/school: `Files.Read` (least), `Files.Read.All`, `Files.ReadWrite`, `Files.ReadWrite.All`, `Sites.Read.All`, `Sites.ReadWrite.All`; for personal accounts only the Files.* scopes. Listed request forms include `/drives/{drive-id}/root/delta`, `/groups/{groupId}/drive/root/delta`, `/sites/{siteId}/drive/root/delta`. — [Graph: driveItem delta](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0)
- rclone's default scope set is `Files.Read Files.ReadWrite Files.Read.All Files.ReadWrite.All Sites.Read.All offline_access`; `Sites.Read.All` is "required if you need to search SharePoint sites when configuring the remote", and rclone offers a reduced scope set (or `disable_site_permission`) "without the ability to browse SharePoint sites" for tenants that will not grant it. — [rclone OneDrive docs](https://rclone.org/onedrive/)
- abraunegg/onedrive's documented example authorisation URL requests `Files.ReadWrite Files.ReadWrite.All Sites.ReadWrite.All offline_access`; it has a `read_only_auth_scope` option, and an admin-consent path (`--display-admin-consent-url`, which requires `azure_tenant_id`). — [abraunegg/onedrive: application-config-options.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/application-config-options.md)
- abraunegg/onedrive also supports `use_device_auth` (device-code flow, "supported for Entra ID work/school accounts but not personal Microsoft accounts", as summarised) and `use_intune_sso` ("Intune Single Sign-On (SSO) via the Microsoft Identity Device Broker over D-Bus", intended for Intune-enrolled systems). — [abraunegg/onedrive: application-config-options.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/application-config-options.md)
- Tenant refusing the app: rclone documents error AADSTS65005 where the organisation has left rclone unprovisioned, so rclone "can't use the OneDrive for Business API with your account"; its suggested fallback is the WebDAV backend. — [rclone OneDrive docs](https://rclone.org/onedrive/)
- Unmanaged devices are "those not hybrid AD joined or compliant in Intune". Under "Allow limited, web-only access", "Users on unmanaged devices have browser-only access with no ability to download, print, or sync files. They also won't be able to access content through apps, including the Microsoft Office desktop apps." — [Microsoft Learn: Control access from unmanaged devices](https://learn.microsoft.com/en-us/sharepoint/control-access-from-unmanaged-devices)
- Under "Block access" users see: "Access Denied. Due to organization policy, you can't access this resource from this untrusted device." — [Microsoft Learn: Control access from unmanaged devices](https://learn.microsoft.com/en-us/sharepoint/control-access-from-unmanaged-devices)
- These controls rely "on Microsoft Entra Conditional Access policies"; they can be tenant-wide (`Set-SPOTenant -ConditionalAccessPolicy AllowLimitedAccess`) or per-site (`Set-SPOSite ... -ConditionalAccessPolicy BlockAccess | AllowLimitedAccess`), or applied through a sensitivity label on the site. `-ReadOnlyForUnmanagedDevices $true` "Makes the entire site read-only for impacted users." — [Microsoft Learn: Control access from unmanaged devices](https://learn.microsoft.com/en-us/sharepoint/control-access-from-unmanaged-devices)
- "Apps that run in 'app-only' mode in the service, like antivirus apps and search crawlers, are exempted from the policy." (i.e. delegated clients are not exempt.) — [Microsoft Learn: Control access from unmanaged devices](https://learn.microsoft.com/en-us/sharepoint/control-access-from-unmanaged-devices)
- Microsoft recommends also blocking "apps that don't use modern authentication" because "Some third-party apps ... can't enforce device-based restrictions." Policy changes "can take up to 24 hours" and do not "take effect for users who are already signed in from unmanaged devices". — [Microsoft Learn: Control access from unmanaged devices](https://learn.microsoft.com/en-us/sharepoint/control-access-from-unmanaged-devices)
- "Allow syncing only on computers joined to specific domains" (cmdlet `Set-SPOTenantSyncClientRestriction`) takes AD domain GUIDs and "is only applicable to Active Directory domains. It doesn't apply to Microsoft Entra domains"; for Entra-joined devices Microsoft directs admins to Conditional Access. The setting applies "to SharePoint sites and OneDrive". — [Microsoft Learn: Allow syncing only on computers joined to specific domains](https://learn.microsoft.com/en-us/sharepoint/allow-syncing-only-on-specific-domains)
- Admins can hide the library Sync button tenant-wide with `Set-SPOTenant -HideSyncButtonOnTeamSite $true`; this "blocks new syncs from being started but doesn't affect existing syncs". — [Microsoft Learn: Sync in SharePoint and OneDrive](https://learn.microsoft.com/en-us/sharepoint/sharepoint-sync)
- Admins can disable shortcuts with `Set-SPOTenant -DisableAddShortcutsToOneDrive $True`. — [Microsoft Support: Add shortcuts to shared folders](https://support.microsoft.com/en-us/office/add-shortcuts-to-shared-folders-in-onedrive-for-work-or-school-d66b1347-99b7-4470-9360-ffc048d35a33)
- Selected scopes: "all Selected scopes now support delegated and application modes". The family is `Sites.Selected` (site collection), `Lists.SelectedOperations.Selected` (a list/library), `ListItems.SelectedOperations.Selected`, `Files.SelectedOperations.Selected`. — [Graph: Overview of Selected permissions](https://learn.microsoft.com/en-us/graph/permissions-selected-overview)
- Selected scopes grant nothing by themselves: "an application consented for Lists.SelectedOperations.Selected would initially have no access". Three steps are all required: consent in Entra ID, an explicit grant such as `POST /sites/{siteid}/lists/{listid}/permissions` with a role (`read`, `write`, `owner`, `fullcontrol`), and a token carrying the scope. — [Graph: Overview of Selected permissions](https://learn.microsoft.com/en-us/graph/permissions-selected-overview)
- Delegated Selected access is an intersection: "both the application and user permissions are calculated and then intersected, which means that the application can never exceed the user's permissions, and the user can never exceed (through the application) the consented application permissions." — [Graph: Overview of Selected permissions](https://learn.microsoft.com/en-us/graph/permissions-selected-overview)
- Granting a site-level permission to an app requires `Sites.FullControl.All`; list-level grants need `Sites.FullControl.All` or a Selected scope with FullControl/Owner on the parent. Assigning at list/item/file level "breaks inheritance on the assigned resource". — [Graph: Overview of Selected permissions](https://learn.microsoft.com/en-us/graph/permissions-selected-overview)
- Processing permission changes in delta (`Prefer: deltashowsharingchanges` etc.) requires `Sites.FullControl.All`. — [Graph: driveItem delta](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0)

### Inferences
- For a consumer-style sync client, `Sites.Selected` in delegated mode is impractical as a default: an admin (or site owner holding a suitable Selected+Owner grant) must pre-authorise the client's app ID on each site or library before the user can sync it, and site search does not work under it. It is, however, a credible "enterprise mode" for security-conscious tenants: the admin grants the client's app `write` on specific libraries and the client requests only `Lists.SelectedOperations.Selected`.
- A reasonable scope strategy is: baseline `Files.ReadWrite.All offline_access` (covers own OneDrive, shortcut targets, `/drives/{id}` for libraries, `/shares`, `filesFolder`); request `Sites.Read.All` incrementally only when the user opens "browse/search sites". rclone's `disable_site_permission` shows the same split in practice.
- Under an unmanaged-device policy a Linux machine is almost always "unmanaged" (not hybrid AD joined; Intune compliance for Linux exists but is tenant-specific), so the client must expect hard 403s / "Access Denied ... untrusted device" on some or all sites, possibly per-site (site-level policy or sensitivity label), and possibly appearing up to 24 hours after sign-in. It needs a per-library "blocked by organisation policy" state rather than a generic sync error, and must tolerate one library failing while others sync.
- abraunegg's `use_intune_sso` (identity broker over D-Bus) indicates the known route for satisfying device-compliance Conditional Access on Linux: obtain tokens through the Microsoft identity broker on an Intune-enrolled machine so the token carries device identity.
- The domain-join restriction is described purely as a sync-app setting keyed to AD domain GUIDs. Since a Graph client does not present a domain GUID, the documentation gives no basis to predict the effect; treat it as unknown and test against a tenant with it enabled.

### Gaps
- Not verified this session (prior knowledge of the Graph permissions reference): that delegated `Files.ReadWrite.All`, `Sites.Read.All` and `Sites.ReadWrite.All` are user-consentable by default while delegated `Sites.Selected`, `Sites.FullControl.All` and the `*.SelectedOperations.Selected` scopes require admin consent. The permissions reference was not fetched; confirm the "AdminConsentRequired" column before publishing. Independently of that column, tenants can disable or restrict user consent for all third-party/unverified-publisher apps, which makes every scope effectively admin-consent; the Entra user-consent settings documentation was not fetched.
- No primary source found on how `Set-SPOTenantSyncClientRestriction` (domain GUID allow-list, and its `-BlockMacSync` / `-GrooveBlockOption` parameters) treats third-party Graph API clients. The cmdlet reference page was not fetched.
- Exact error codes/bodies Graph returns to a delegated app when blocked by app-enforced restrictions or by a block-download policy (`Set-SPOSite -BlockDownloadPolicy`) were not found. The unmanaged-devices page mentions a "block download policy" only in passing.
- Whether Conditional Access "require approved client app / app protection policy" grants can ever be satisfied by a third-party Linux client was not researched.

## 3. The two Windows models: "Sync" button vs "Add shortcut to My files"

### Takeaway
Microsoft recommends shortcuts over the Sync button. For a Graph client the two map to different mechanics: Sync means a separate drive with its own delta token and its own local root; a shortcut is an item inside the user's own drive that points at a folder in another drive, which the client must follow and delta-track separately. Shortcut handling over Graph is the weaker path: the one public bug report on shortcuts missing from business `/delta` was closed without a documented fix, and listing through shortcuts is known to throw errors in rclone.

### Cited Findings
- Microsoft: "Both OneDrive shortcuts and OneDrive Sync options allow essentially the same thing ... However, adding OneDrive shortcuts allows content to be accessed on all devices, whereas sync is related to a specific device. Additionally, OneDrive shortcuts offer improved performance versus using the sync button. We recommend using OneDrive shortcuts as the more versatile option." — [Microsoft Learn: Sync in SharePoint and OneDrive](https://learn.microsoft.com/en-us/sharepoint/sharepoint-sync)
- The end-user article repeats it: "We recommend using OneDrive shortcuts as the more versatile option when available." — [Microsoft Support: Sync SharePoint and Teams files with your computer](https://support.microsoft.com/en-us/office/sync-sharepoint-and-teams-files-with-your-computer-6de9ede8-5b6e-4503-80b2-6190f3354a88)
- Sync button model: "The files then sync to a folder on your PC that has the name of your organization" (example `%userprofile%\Contoso`); "This folder is automatically added to the left pane in File Explorer"; "You can't select to sync to a different location." Sync is per device: "To sync the files on another computer, go to that computer, and follow these steps again." — [Microsoft Support: Sync SharePoint and Teams files with your computer](https://support.microsoft.com/en-us/office/sync-sharepoint-and-teams-files-with-your-computer-6de9ede8-5b6e-4503-80b2-6190f3354a88)
- Shortcut model: a shortcut can target "the entire library or ... a specific folder inside it" (SharePoint/Teams), appears in My files and inside the user's own sync root ("OneDrive - Contoso"), and follows the account to every device. — [Microsoft Support: Add shortcuts to shared folders](https://support.microsoft.com/en-us/office/add-shortcuts-to-shared-folders-in-onedrive-for-work-or-school-d66b1347-99b7-4470-9360-ffc048d35a33)
- Shortcut limits: "You can only add shared folders to your OneDrive, not individual shared files"; "You can't add shortcuts to folders that are shared with external users"; unavailable once "You already added 100 shortcuts in the same document library"; a stated ceiling of 1,000 shortcuts overall (as summarised). Shortcut contents "don't use any of your OneDrive storage space". — [Microsoft Support: Add shortcuts to shared folders](https://support.microsoft.com/en-us/office/add-shortcuts-to-shared-folders-in-onedrive-for-work-or-school-d66b1347-99b7-4470-9360-ffc048d35a33)
- Shortcut semantics a client must reproduce: renaming a shortcut is private ("The new name you give to the folder is visible only to you") while renaming contents is global; shortcuts can be moved like any item; removing the shortcut removes it only for the user, but "If you delete the folder instead, it's deleted from everyone's OneDrive". If access is revoked, the shortcut "is removed from your OneDrive". — [Microsoft Support: Add shortcuts to shared folders](https://support.microsoft.com/en-us/office/add-shortcuts-to-shared-folders-in-onedrive-for-work-or-school-d66b1347-99b7-4470-9360-ffc048d35a33)
- Microsoft's own client has destructive edge cases here: deleting a shortcut while files inside are open "results in deletion of some or all files within the shortcut", and deleting an expanded shortcut from the Windows navigation pane deletes the folder and contents for everyone (as summarised). — [Microsoft Support: Add shortcuts to shared folders](https://support.microsoft.com/en-us/office/add-shortcuts-to-shared-folders-in-onedrive-for-work-or-school-d66b1347-99b7-4470-9360-ffc048d35a33)
- Known issue acknowledged by Microsoft: some shortcuts appear as `.url` internet shortcuts instead of folders; "The .url internet shortcuts automatically convert back to a folder when the issue is resolved." — [Microsoft Support: Add shortcuts to shared folders](https://support.microsoft.com/en-us/office/add-shortcuts-to-shared-folders-in-onedrive-for-work-or-school-d66b1347-99b7-4470-9360-ffc048d35a33)
- Shortcuts missing from delta: OneDrive/onedrive-api-docs issue #1427, "ODB: OneDrive API does not report 'sharepoint links' when using /delta", opened 21 Jan 2021 by abraunegg. A SharePoint link added to My Files "is not presented in any way via the API" in `/delta`. A Microsoft contributor asked for confirmation; no fix or explanation was posted; it was closed on 17 Feb 2023 with "As part of a repository clean up effort we are closing older issues" and locked. — [OneDrive/onedrive-api-docs issue #1427](https://github.com/OneDrive/onedrive-api-docs/issues/1427)
- abraunegg/onedrive nevertheless now syncs business shared folders that have been added as shortcuts: the feature "was 100% re-written from v2.5.0 onwards", is enabled with `sync_business_shared_items = "true"`, requires a `--resync`, and requires the user to first use "Add shortcut to My files" in the web UI. — [abraunegg/onedrive: business-shared-items.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/business-shared-items.md)
- rclone on shortcuts: listing a shortcut may fail with "invalidRequest: The provided drive id appears to be malformed"; the workaround is `--disable ListR`, since `--fast-list` (delta-based recursive listing) stops at the first error. rclone has no direct "Shared with me" support; the documented workaround is adding a shortcut to My files. — [rclone OneDrive docs](https://rclone.org/onedrive/)
- Per-drive delta: delta is requested per drive (`/drives/{drive-id}/root/delta`, `/sites/{siteId}/drive/root/delta`, `/groups/{groupId}/drive/root/delta`), and the response is that drive's hierarchy only. — [Graph: driveItem delta](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0)
- The Graph delta page lists only `.../root/delta` request forms. rclone states that some drives, "as some older OneDrive for Business and SharePoint drives do", only support delta from the root. — [Graph: driveItem delta](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0); [rclone OneDrive docs](https://rclone.org/onedrive/)
- An unverified community report (RaiDrive forum, surfaced only as a search snippet, page not opened) says adding the request header `Prefer: Include-Feature=AddToOneDrive` makes shortcut items appear, and links it to issue #1427. — [RaiDrive community thread](https://with.raidrive.com/t/microsoft-onedrive-business/7619)

### Inferences
- A shortcut to a library folder cannot be synced from the user's own drive delta alone. The user-drive delta (at best) yields a stub item with a `remoteItem` facet naming the target `driveId`/item id; the content lives in the library's drive. The client must therefore keep, per shortcut, a second change-tracking stream against the target drive and graft the results under the shortcut's local path. Since delta is reliably available only at a drive root, a shortcut to one folder in a 200,000-item library implies either a root delta on the whole library filtered client-side, or a folder-scoped delta where the service supports it, or polling `children`. This cost model is the main engineering argument for treating "Sync a library as its own root" as the primary, robust path and shortcuts as a compatibility feature.
- Internally both models should share one abstraction: a "mounted drive" = (driveId, optional root item id, local mount point, delta token). The Sync model mounts at `~/<Org>/<Site> - <Library>`; a shortcut mounts inside the OneDrive root at the shortcut's (user-renamable, user-movable) path.
- De-duplication is needed: the same library folder can be reachable both as a directly synced library and through a shortcut. Microsoft's article does not say how its client resolves the overlap, so the client should detect identical (driveId, itemId) targets and refuse or merge.
- Delete handling must distinguish "user removed the shortcut stub" (delete the stub item in the user's drive only) from "user deleted content inside the shortcut" (delete in the target drive, affecting everyone). Microsoft's documented data-loss cases show this is the highest-risk part of shortcut support; a conservative client should never translate removal of a mount directory into recursive remote deletes.
- Because shortcut names are private renames, the local folder name must come from the stub item in the user's drive, not from the target folder's name.

### Gaps
- The `remoteItem` resource documentation was not fetched this session (the earlier note `graph_api_and_windows_parity.md` already has some remoteItem coverage). The exact shape of a business shortcut stub in delta in late 2026 (whether it appears by default, whether it carries `remoteItem.parentReference.driveId`, `remoteItem.sharepointIds`) needs a live test.
- `Prefer: Include-Feature=AddToOneDrive` is undocumented by Microsoft as far as this research found; its existence rests on one forum thread seen only as a snippet. I did not confirm from abraunegg's source code how v2.5.x discovers shortcuts (header vs. `children` enumeration vs. another call). This should be checked in `src/onedrive.d`/`src/sync.d` before design decisions are made.
- No Microsoft statement found on whether shortcuts into a different tenant or a different geo resolve through Graph.
- Not confirmed from a primary source: behaviour when a user both syncs a library and adds a shortcut to the same library in Microsoft's client.

## 4. SharePoint-specific behaviours that break sync clients

### Takeaway
The most damaging SharePoint-specific behaviour is that the server rewrites some uploaded files, so the stored size and hash differ from what the client sent; every existing Linux client has needed a special case for it. Libraries with required check-out, validation or restricted draft visibility are synced read-only by Microsoft's own client, which a Linux client should copy rather than fight. Naming rules and item-count guidance are stricter than a typical Linux filesystem and need pre-upload validation.

### Cited Findings
Server-side file modification
- rclone: SharePoint "silently modifies uploaded files," mainly Office files, which breaks size and hash checks; the documented workaround is `--ignore-checksum --ignore-size` (or opening affected files in the web UI so they are converted once). — [rclone OneDrive docs](https://rclone.org/onedrive/)
- rclone also documents "item not found" errors when replacing or deleting existing files on SharePoint, mainly Office and web files, with `--backup-dir` on the same remote as the workaround. — [rclone OneDrive docs](https://rclone.org/onedrive/)
- abraunegg/onedrive: SharePoint can modify a file after upload so the local copy no longer matches the online copy; its upload handling was rewritten in v2.5.0. Options: `disable_upload_validation` (skip post-upload integrity check because SharePoint may modify uploaded files), `disable_download_validation` (noted as relevant to SharePoint, Business shared folders and Azure Information Protection files), and `create_new_file_version`, which "controls how the application handles the Microsoft SharePoint *feature*": when enabled the client uploads again as a new online version instead of downloading the server-modified file, at the cost of quota. — [abraunegg/onedrive: sharepoint-libraries.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/sharepoint-libraries.md); [abraunegg/onedrive: application-config-options.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/application-config-options.md)
- A Microsoft Q&A answer (community-grade source, seen as a search snippet) attributes the cause to SharePoint "property promotion", which "modifies Office files, emails (eml and msg) and tiff files", adding "schema (xsd) information, custom columns and the content type details into the file", producing "a small file size increase (several kB's)" and making checksums "useless". — [Microsoft Q&A: SharePoint modifying internal file structure of Word document on upload](https://learn.microsoft.com/en-us/answers/questions/513739/sharepoint-modifying-internal-file-structure-of-wo)
- abraunegg's SharePoint guide opens with a data-loss warning about files being overwritten, naming desktop file indexers (Baloo, Tracker3) and WPS Office (which saves by delete-and-replace) as triggers, and recommends against running SharePoint syncs under systemd and against indexing the synced data (paraphrased by the fetch tool; exact version numbers were not captured). — [abraunegg/onedrive: sharepoint-libraries.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/sharepoint-libraries.md)

Delta and versions on SharePoint
- On OneDrive for Business/SharePoint, delta omits `ctag` on create/modify and omits `ctag` and `name` on delete; `parentReference.path` is never included. — [Graph: driveItem delta](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0)
- "Using a timestamp in place of a token is only supported on OneDrive for Business and SharePoint." — [Graph: driveItem delta](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0)
- Versioning cost: each change creates a version that counts against quota; single-part uploads "can double storage use on OneDrive Business, because setting modification time creates a new version"; setting folder mtime/btime "requires one extra API call on OneDrive Business only". — [rclone OneDrive docs](https://rclone.org/onedrive/)
- Deletion: deleted files go to the recycle bin; rclone's `hard_delete` works with "SharePoint document libraries", and abraunegg's `permanent_delete` is supported for Business and SharePoint but not Personal or US Government accounts. — [rclone OneDrive docs](https://rclone.org/onedrive/); [abraunegg/onedrive: application-config-options.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/application-config-options.md)
- Upload chunks above roughly 250M can trigger "Microsoft.SharePoint.Client.InvalidClientQueryException: The request message is too big." — [rclone OneDrive docs](https://rclone.org/onedrive/)

### Inferences
- After every upload to a `documentLibrary` drive (and to OneDrive for Business, which is SharePoint underneath), the client should treat the server's response metadata (size, quickXorHash, eTag) as the new truth for the item and record that the local bytes are a known "pre-enrichment" equivalent, instead of flagging a conflict or re-downloading. Concretely: store both `local_hash_at_upload` and `server_hash_after_upload`; the file is in sync if the local content still hashes to the former and the server still reports the latter. This avoids all three failure modes seen in existing clients: endless re-upload loops, re-download that rewrites the user's file (which is what trips indexers and delete-and-replace editors in abraunegg's warning), and disabling validation globally.
- Files On-Demand makes this easier than it is for full-mirror clients: an uploaded file can be left hydrated with the local bytes while the placeholder metadata takes the server's size/hash; only a later genuine server change triggers re-hydration.
- Read-only detection should be proactive, not error-driven. Inputs available over Graph are per-item permissions/role, the library's list settings (forced checkout, validation, draft visibility, required columns), and per-item `publication` (checked-out) state. When a library is in this state, mirror Microsoft: mark the mount read-only (mode bits plus a lock emblem) and do not attempt uploads, rather than uploading files that land checked-out to the uploader and invisible to everyone else.
- Linux filename validation must run before upload for both own-drive and library mounts: reject or queue-with-error names containing the forbidden characters, reserved device names, `~$` prefixes, `_vti_`, root-level `forms`, trailing spaces, and over-400-character paths. Linux allows all of these and allows names differing only by case; SharePoint is case-insensitive, so two local files differing only in case must be surfaced as a conflict.
- The 400-character limit applies to the server-side path, which for a library includes the site and library path segments, so the usable budget under a library root is smaller than under a personal OneDrive and differs per library.
- The 300,000-item guidance is about Microsoft's client's local bookkeeping, not a Graph limit, but it is a useful warning threshold: adding a library should show its item count and warn when the combined total crosses about 300,000.

### Gaps
- No primary Microsoft documentation of property promotion (which file types, whether it can be disabled, whether a second modification happens asynchronously after upload returns) was fetched; the mechanism rests on a Q&A answer plus rclone/abraunegg descriptions. One search snippet claimed it "cannot be disabled in SharePoint Online", another that it "can only be disable on a tenant level"; these conflict and neither is authoritative.
- Retention / Preservation Hold: no source found this session on what Graph returns when a delete or overwrite is attempted on an item under a retention label, record lock or hold, nor on how the Preservation Hold Library appears among a site's drives. The only relevant finding is that removing a records retention label needs `Sites.FullControl.All` ([driveItem: removeRetentionLabel](https://learn.microsoft.com/graph/api/driveitem-removeretentionlabel)), which a sync client would not hold. Must be tested.
- 5,000-item list view threshold: not found in the fetched pages (the 5,000 figure that appeared there is the recommended unique-permissions limit). Whether Graph `children` listing or `$filter`/`$orderby` on large library folders fails with a threshold error was not verified. Delta enumeration is the documented reliable way to enumerate a full drive.
- The exact way the 400-character limit is counted (decoded path, which segments are included) lives in a separate Microsoft article that was not fetched.
- Sensitivity labels: beyond site-level labels driving unmanaged-device policy (section 2) and abraunegg's note that Azure Information Protection files can fail download validation, no source was found on how label-encrypted files or label-based download blocking behave through Graph for a third-party client.
- Check-out: the Graph `checkout`/`checkin` driveItem actions and the `publication` facet were not fetched; how an upload behaves in a forced-check-out library (auto check-out to the uploader, error, or minor version) is unverified.
- Whether SharePoint also modifies PDFs was asserted in the research brief but not corroborated by any source fetched; the sources name Office files, eml/msg and TIFF.

## 5. How existing clients handle SharePoint

### Takeaway
abraunegg/onedrive and rclone both model a library as a separate drive selected by drive ID, with one configuration (and one authentication) per library; neither offers an in-app picker beyond a site-name search. Both document the same SharePoint pain points (server-modified files, shortcut quirks, scope/consent refusals), which is good evidence of what a new client must solve by design rather than by flags.

### Cited Findings
abraunegg/onedrive
- Workflow: find the library name in the OneDrive web UI "Shared Libraries" section; run `--get-sharepoint-drive-id '<site name>'` (needs a working authenticated config), which prints site name, library name, `drive_id` and library URL; if nothing matches it lists the site names it did find. — [abraunegg/onedrive: sharepoint-libraries.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/sharepoint-libraries.md)
- One library = one config directory + one `sync_dir` + one `drive_id`: e.g. `~/.config/SharePoint_My_Library_Name` and `~/SharePoint_My_Library_Name` (names without spaces). Changing `drive_id` requires `--resync`. The user is "asked to re-authorise the first time for each new configuration". For several libraries, "Repeat the whole process for each library, with a separate config directory, sync folder, and service file." — [abraunegg/onedrive: sharepoint-libraries.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/sharepoint-libraries.md)
- Each library needs its own copied systemd unit with an explicit `--confdir` (and `~` expanded by hand); the guide simultaneously recommends against systemd for SharePoint sync because of the overwrite/data-loss risk. — [abraunegg/onedrive: sharepoint-libraries.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/sharepoint-libraries.md)
- `drive_id` "controls the specific drive identifier the client will use" and "is typically used to sync a specific SharePoint library" (as summarised). — [abraunegg/onedrive: application-config-options.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/application-config-options.md)
- Business shared folders: only via web-UI shortcut plus `sync_business_shared_items = "true"`; the v2.5.0 rewrite is not compatible with v2.4.x (old `sync_business_shared_folders` option and `business_shared_folders` file must be removed, and every machine upgraded). Client-side filtering rules (`sync_list` etc.) apply inside shared folders. — [abraunegg/onedrive: business-shared-items.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/business-shared-items.md)
- Shared files: Option 1, a shortcut to a single file becomes a local `.url` file that opens the browser; Option 2, `--sync-shared-files` downloads everything shared with the user into "Files Shared With Me/<sharer name>/" (filter with `--list-shared-items` + `sync_list`); read-only items without download rights give HTTP 403 and are skipped. — [abraunegg/onedrive: business-shared-items.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/business-shared-items.md)
- `monitor_fullscan_frequency` schedules periodic "online full-scan true-up passes" that bypass the stored delta link. — [abraunegg/onedrive: application-config-options.md](https://raw.githubusercontent.com/abraunegg/onedrive/master/docs/application-config-options.md)

rclone
- Config wizard drive choices: "1 / OneDrive Personal or Business", "2 / Sharepoint site", "3 / Type in driveID", "4 / Type in SiteID", "5 / Search a Sharepoint site"; `drive_type` is one of `personal | business | documentLibrary`. — [rclone OneDrive docs](https://rclone.org/onedrive/)
- Site search requires `Sites.Read.All`; with client-credentials auth only the "sharepoint" or "driveid" choices work ("the "onedrive" option does not work"). — [rclone OneDrive docs](https://rclone.org/onedrive/)
- A non-admin escape hatch exists: set `tenant_url` to the SharePoint tenant's own API (e.g. `https://your-tenant.sharepoint.com/_api`, `tenant_api_version` v2.0/v2.1) with a manually supplied token, bypassing the Graph endpoint. — [rclone OneDrive docs](https://rclone.org/onedrive/)
- Pitfalls it documents for SharePoint: size/hash mismatch after upload; "item not found" on replace/delete; versions consuming quota (`no_versions`, or admin `Set-SPOTenant -EnableMinimumVersionRequirement $False`); public links refused where admins disallow them; AADSTS65005 when the tenant has not provisioned the app; throttling eased by a decorated user agent such as `ISV|rclone.org|rclone/v1.55.1`. — [rclone OneDrive docs](https://rclone.org/onedrive/)
- Recently changed (flag): rclone tells users to "Upgrade to rclone v1.76 or later before April 1, 2027" because of the pre-authenticated URL retirement, with the failure mode "SharePoint refused to authenticate a request"; it also notes SharePoint does not accept client-secret tokens from the client-credentials flow. — [rclone OneDrive docs](https://rclone.org/onedrive/)
- A university guide shows the typical user flow: choose "SharePoint site name or URL" in `rclone config`, paste the site URL, then pick the library. — [UvA staff blog: Mount UvA OneDrive and SharePoint libraries on Linux with rclone](https://staff.fnwi.uva.nl/p.vanormondt/blog/2021-04-30-mount-onedrive-on-linux-with-rclone.html)

Insync
- Insync advertises SharePoint support on Linux: sign in with the Microsoft account, a SharePoint tab appears, and the user picks what to sync with "Cloud Selective Sync" into the Base Folder (from a search snippet of Insync's marketing page; page not opened). — [Insync: SharePoint](https://www.insynchq.com/i/onedrive/sharepoint)

### Inferences
- The main UX gap in the open-source clients is exactly what the new client needs: one sign-in, one daemon, many drives. abraunegg requires a separate config directory, re-authentication, resync and service unit per library; rclone requires one remote per library. A single account object holding N mounted drives (each with its own delta token and state database partition) would be a clear improvement, and matches how Windows presents it.
- Both tools resolve a site by name/URL and then let the user pick a library, and both also accept a raw drive ID. A new client should offer: paste URL, browse Teams, search sites (if scope granted), and "enter drive ID" as an expert fallback.
- abraunegg's scheduled full-scan true-up indicates that delta alone has not proved fully trustworthy in production on Business/SharePoint drives; a periodic low-priority reconciliation pass per mounted drive is prudent.
- abraunegg's indexer warning is directly relevant to an on-demand client: indexers and thumbnailers opening files inside a SharePoint mount must not cause hydration, modification-time changes or re-uploads.

### Gaps
- GNOME/gvfs: not researched this session (see `existing_clients.md`). I found no evidence in this session's sources on whether the GNOME Online Accounts Microsoft 365 backend exposes SharePoint libraries or only the user's own drive.
- Insync: only a marketing snippet was seen; no documentation of how Insync discovers sites, whether it supports Teams private/shared channels, or which scopes it requests. Its limitations with SharePoint are undocumented in what was found.
- abraunegg's exact wording of the data-loss warning and the version it names were paraphrased by the fetch tool; re-read the raw file before quoting. Its specific SharePoint-related issue numbers (other than #966 and onedrive-api-docs #1427) were not collected.
- Whether abraunegg supports selecting a Teams channel directly, or cross-tenant libraries, was not found.

## 6. Windows presentation: sync roots, icons, read-only libraries

### Takeaway
Windows shows the user's own OneDrive as "OneDrive - <Org>" and all synced libraries from that tenant under a second, separate root named after the organisation; shortcuts instead appear inside "OneDrive - <Org>" with a chain-link folder icon. Read-only library content shows a lock icon and local edits simply do not sync.

### Cited Findings
- Synced libraries land in "a folder on your PC that has the name of your organization" (example `%userprofile%\Contoso`), which "is automatically added to the left pane in File Explorer"; the location cannot be changed at sync time. — [Microsoft Support: Sync SharePoint and Teams files with your computer](https://support.microsoft.com/en-us/office/sync-sharepoint-and-teams-files-with-your-computer-6de9ede8-5b6e-4503-80b2-6190f3354a88)
- The user's own work OneDrive (and any shortcuts in it) appears as "the OneDrive folder with your organization's name, for example 'OneDrive - Contoso'". — [Microsoft Support: Add shortcuts to shared folders](https://support.microsoft.com/en-us/office/add-shortcuts-to-shared-folders-in-onedrive-for-work-or-school-d66b1347-99b7-4470-9360-ffc048d35a33)
- "File Explorer shows only the first 35 characters of a library and site name combination." — [Microsoft Support: Restrictions and limitations](https://support.microsoft.com/en-us/office/restrictions-and-limitations-in-onedrive-and-sharepoint-64883a5d-228e-48f5-b3d2-eb39e07630fa)
- Account limits: one OneDrive for home account and nine work or school accounts per device; on macOS only one business account from the same organisation at a time. — [Microsoft Support: Restrictions and limitations](https://support.microsoft.com/en-us/office/restrictions-and-limitations-in-onedrive-and-sharepoint-64883a5d-228e-48f5-b3d2-eb39e07630fa)
- Per-library management: "To change the folders that you're syncing, select Choose folders for that library"; "To stop syncing a site, select Stop sync next to the site." After stopping, "Copies of the files remain on your computer." — [Microsoft Support: Sync SharePoint and Teams files with your computer](https://support.microsoft.com/en-us/office/sync-sharepoint-and-teams-files-with-your-computer-6de9ede8-5b6e-4503-80b2-6190f3354a88)
- Read-only: "If you see a lock icon on synced files in File Explorer, it means the files are synced read-only." "If you change the files on your computer, the changes won't sync." — [Microsoft Support: Sync SharePoint and Teams files with your computer](https://support.microsoft.com/en-us/office/sync-sharepoint-and-teams-files-with-your-computer-6de9ede8-5b6e-4503-80b2-6190f3354a88)
- Icons documented in the icon reference: blue cloud outline (online-only); cloud with person (shared); "Folder with a chain link: The folder is a shortcut to another folder that is shared"; white circle with green tick (locally available); solid green circle with white tick ("Always keep on this device"); red circle with white cross (cannot sync). The padlock and any library-specific icon are not described on that page. — [Microsoft Support: What do the OneDrive icons mean?](https://support.microsoft.com/en-us/office/what-do-the-onedrive-icons-mean-11143026-8000-44f8-aaa9-67c985aa49b3)
- Removing a shortcut from File Explorer is an explicit command (right-click → OneDrive → Remove shortcut), distinct from deleting the folder. — [Microsoft Support: Add shortcuts to shared folders](https://support.microsoft.com/en-us/office/add-shortcuts-to-shared-folders-in-onedrive-for-work-or-school-d66b1347-99b7-4470-9360-ffc048d35a33)

### Inferences
- The Linux equivalent layout is: `~/OneDrive` (personal), `~/OneDrive - <Org>` per work account, and `~/<Org>/` per tenant containing one directory per synced library; shortcuts live inside `~/OneDrive - <Org>` at their stub's path. With up to nine work accounts, two accounts in the same tenant would collide on `~/<Org>`; the client needs a disambiguation rule.
- The Files On-Demand status set applies unchanged inside library roots; the two extra emblems to implement are the lock overlay (read-only item/library) and the chain-link folder overlay (shortcut mount). "Remove shortcut" and "Stop syncing this library" should be explicit context-menu actions that never issue recursive remote deletes; stopping a library should leave or optionally purge local copies, as Windows leaves them.
- Read-only library mounts should be enforced at the filesystem layer (deny writes/creates with EROFS or EACCES at the FUSE/kernel layer) because Windows merely ignores local edits, which silently strands user changes; on Linux an up-front refusal is both possible and safer.
- Library folder names should be sanitised when derived from site/library display names: Microsoft's client refuses to sync a site whose name contains a character invalid on Windows, whereas on Linux only `/` and NUL are invalid, so sanitising is enough.

### Gaps
- The naming pattern of library folders inside the organisation root (commonly seen as "<Site name> - <Library name>") was not stated on the fetched pages; the 35-character note implies a site-plus-library combination but the exact format is unverified.
- The "building" icon for the organisation root in the File Explorer navigation pane was not confirmed by any source found.
- How Windows presents libraries from a second tenant under a guest/B2B identity, or two accounts in the same tenant, was not documented in the pages fetched.
- Whether read-only library files are hydrated/dehydrated differently, and the exact dialog shown when a user edits a locked file, were not found in primary sources (only old Tech Community threads describing green padlocks).
