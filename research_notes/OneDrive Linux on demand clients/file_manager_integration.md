# File-manager and desktop integration surfaces for a Linux cloud sync client (as of November 2026)

Conventions used in these notes:

- "[local]" marks a fact verified by direct inspection of the research machine, which is itself an Omarchy install (`omarchy 4.5.0-3`, `nautilus 51.1-1`, `hyprland 0.56.2-4`, kernel `7.2.15-1-omarchy`), on 2026-11-14. These have no URL; the commands used were `pacman -Q/-Qi/-Ql/-Si`, `ldd`, `busctl --user list`, `systemctl --user`, `xdg-mime`, `gsettings`, and reading files under `/usr/share/omarchy`.
- "UNVERIFIED (background knowledge)" marks things I believe to be true from prior knowledge but did not confirm against a source in this session. They are kept in the Gaps/Inferences sections, never in Cited Findings.
- Research budget was exceeded (about 30 tool calls against a suggested 15) because of scope; several file managers are still only covered in Gaps.

## 1. Per file manager: extension mechanisms and their limits

### Takeaway
Only the Nautilus family (Nautilus, Nemo, Caja) and Dolphin have a verified first-class API for per-file status emblems plus dynamic context menus; Thunar's public thunarx-3 `FileInfo` has no emblem function, COSMIC Files has only user-defined context-menu actions, and terminal file managers need a per-tool plugin (yazi has a real async "fetcher" API). On Nautilus 43+ (GTK4, extension API 4) an extension is model-only: emblems, menu items, list columns and text-only property pages; no widgets, no location bar, no double-click/activation hook.

### Cited Findings

**Nautilus (libnautilus-extension 4, GTK4)**
- The libnautilus-extension 4 API surface is exactly: interfaces `ColumnProvider` ("additional list view columns"), `FileInfo`, `InfoProvider` ("additional information about files"), `MenuProvider` ("additional menu items"), `PropertiesModelProvider` ("additional properties"); classes `Column`, `Menu`, `MenuItem`, `PropertiesItem`, `PropertiesModel`; `OperationHandle`/`OperationResult` for asynchronous interfaces; and module entry points `module_initialize`, `module_list_types`, `module_shutdown`. — [Nautilus extension API reference](https://gnome.pages.gitlab.gnome.org/nautilus/)
- `Nautilus.FileInfo` exposes `add_emblem` ("Attaches an emblem to the file"), `add_string_attribute`, `get_string_attribute`, `invalidate_extension_info` ("Invalidates the currently cached extension information"), plus `get_location`, `get_uri`, `get_uri_scheme`, `get_mount`, `get_mime_type`, `is_mime_type`, `get_file_type`, `is_directory`, `is_gone`, `can_write`, `get_name`, `get_activation_uri`, `get_parent_info/location/uri`. The reference page is headed "API Version 4.1, Library Version 52.alpha" and carries no per-method deprecation notes. — [Nautilus.FileInfo](https://gnome.pages.gitlab.gnome.org/nautilus/iface.FileInfo.html)
- Removed/changed in the GTK4 port (Nautilus 43, extension API 3 -> 4): extensions can no longer manipulate GTK widgets directly; `LocationWidgetProvider` was removed with no replacement; `PropertyPageProvider` was replaced by `PropertiesModelProvider`, which supports only a predefined layout of pages showing text properties; `MenuProvider.get_file_items` / `get_background_items` (and `_full` variants) lost their `window` argument. A single script can support both API 3 and 4 by using `*args` and reading files from `args[-1]`, and by testing `hasattr(Nautilus, "PropertiesModelProvider")`. GTK3 and GTK4 cannot coexist in one process, so any dialog an extension wants must be GTK4 or live in a separate launched program. — [nautilus-python: Migrating to 4.0](https://gnome.pages.gitlab.gnome.org/nautilus-python/nautilus-python-migrating-to-4.html)
- Nautilus offers no hook for double-click, so an extension cannot override file activation; live emblem refresh is "best-effort" and emblems are only reliably correct after F5; a third-party extension has to ship its own emblem icons because "Current Adwaita has pruned its stock emblem set". (Statements by the wusel project, which ships a C `libnautilus-extension` module; one project's experience, not GNOME documentation.) — [wusel 0.4.0 desktop integration](https://wusel.itbh.at/wusel/0.4.0/explanation/desktop-integration.html)
- A C Nautilus extension doing one status query per file measured about 230 microseconds per query, about 46 ms for a cold 200-file folder and about 65 microseconds warm, so the extension must cache and invalidate on a daemon change signal. — [wusel status protocol](https://wusel.itbh.at/wusel/latest/explanation/status-protocol.html)
- [local] Arch/Omarchy ships Nautilus 51.1; compiled extensions load from `/usr/lib/nautilus/extensions-4/` (present: `libnautilus-python.so`, `libnautilus-image-properties.so`, `libpapers-document-properties.so`, `libtotem-properties-page.so`). nautilus-python 4.2.0 is installed, and Python extensions are loaded from `~/.local/share/nautilus-python/extensions/` (system-wide equivalent `/usr/share/nautilus-python/extensions/`, which is where Nextcloud installs: see next bullet).
- Nextcloud installs its Nautilus script to `${CMAKE_INSTALL_DATADIR}/nautilus-python/extensions`, renamed `syncstate-${APPLICATION_SHORTNAME}.py`. — [nextcloud/desktop shell_integration/nautilus/CMakeLists.txt](https://raw.githubusercontent.com/nextcloud/desktop/master/shell_integration/nautilus/CMakeLists.txt)

**Nemo and Caja**
- Nextcloud generates its Nemo and Caja extensions from the same `syncstate.py` by string replacement (`createnemoplugin.sh`, `createcajaplugin.sh`) and installs them to `share/nemo-python/extensions` and `share/caja-python/extensions`. This shows the three APIs are close enough for one Python source to serve all three. — [nextcloud/desktop shell_integration/nautilus/CMakeLists.txt](https://raw.githubusercontent.com/nextcloud/desktop/master/shell_integration/nautilus/CMakeLists.txt)
- [local] Arch `extra` currently packages `nemo 6.6.4-1` and `nemo-emblems 6.6.0-4` (among other nemo extensions), so Nemo remains actively packaged with an emblem extension.

**Thunar (thunarx-3)**
- The public `ThunarxFileInfo` interface has 14 functions (`get_name`, `get_uri`, `get_parent_uri`, `get_uri_scheme`, `get_mime_type`, `has_mime_type`, `is_directory`, `get_file_info`, `get_filesystem_info`, `get_location`, `changed`, `renamed`, list copy/free) and two signals (`changed`, `renamed`). There is no emblem function. — [ThunarxFileInfo reference](https://developer.xfce.org/thunar/ThunarxFileInfo.html)
- An emblem API (`thunarx_file_info_add_emblem` / `remove_emblem` / `remove_emblems`) was proposed and discussed in 2009 but is absent from the current reference above. — [Xfce bug 6055](https://bugzilla.xfce.org/show_bug.cgi?id=6055)
- Thunar stores its own user-set emblems in the GIO `metadata::emblems` attribute, and a Thunar issue reports that emblems changed outside Thunar (for example with `gio set`) do not appear until the folder is re-entered or refreshed; the issue was closed without a fix. — [Thunar issue 630](https://gitlab.xfce.org/xfce/thunar/-/issues/630)
- [local] Arch `extra` has `thunar 4.20.10-1`.

**Dolphin (KDE Frameworks 6)**
- `KOverlayIconPlugin` was moved into KIOCore for KF6 (task marked done February 2023), so a KF6 overlay plugin links against `KF6::KIOCore`. — [KDE Phabricator T14538](https://phabricator.kde.org/T14538)
- Overlay order matters: the first overlay icon is painted at the bottom-right corner. — [KIconUtils API docs](https://api.kde.org/frameworks/kguiaddons/html/namespaceKIconUtils.html)
- A real shipped client (Insync) installs two separate plugins for Plasma 6: one under `qt6/plugins/kf6/kfileitemaction/` (context menu) and one under `qt6/plugins/kf6/overlayicon/` (overlays). — [Insync forum: insync-dolphin and Plasma 6](https://forums.insynchq.com/t/insync-dolphin-does-not-work-with-plasma-6-new-version-available/19800?page=4)
- The KF5 -> KF6 transition broke third-party plugins: the Nextcloud Dolphin plugin "doesn't support KF6 yet" in March 2024, with upstream support reported in Nextcloud desktop v3.13.0. — [KDE bug 483423](https://bugs.kde.org/show_bug.cgi?id=483423)
- A distro-level failure mode: openSUSE shipped `nextcloud-desktop-dolphin` built against Qt5 (`/usr/lib64/qt5/plugins/kf5/kfileitemaction`), so overlay icons vanished in KF6 Dolphin. Compiled plugins must match the file manager's Qt/KF major version. — [openSUSE bug 1221923](https://lists.opensuse.org/archives/list/bugs@lists.opensuse.org/thread/MUO5Z6HLHN3L2K5ZNBSQXDANE4RGXVBZ)
- Dolphin has had overlay rendering regressions (Dolphin 24.12 inconsistent overlay sizes; a later offset-placement bug). — [KDE bug 497372](https://bugs.kde.org/show_bug.cgi?id=497372); [KDE bug 500428](https://bugs.kde.org/show_bug.cgi?id=500428)
- wusel plans Dolphin support as `KOverlayIconPlugin` plus declarative ServiceMenus for actions, and notes Dolphin has no account-level sync status surface (no libcloudproviders consumer). — [wusel 0.4.0 desktop integration](https://wusel.itbh.at/wusel/0.4.0/explanation/desktop-integration.html)
- [local] Arch `extra` has `dolphin-plugins 26.08.2-1`.

**COSMIC Files**
- No extension or plugin API for emblems was found. COSMIC 1.0.10 added user-defined context-menu actions to Files (a configuration feature, not a plugin interface). — [Linuxiac: COSMIC 1.0.10](https://linuxiac.com/cosmic-desktop-1-0-10-brings-new-file-manager-actions/)

**Terminal file managers**
- yazi has a plugin type called a "fetcher" that retrieves per-file metadata asynchronously and in batches, with priorities; the official `git.yazi` plugin uses it to show Git status as a linemode in the file list, registered in `yazi.toml` for files and directories and enabled with `require("git"):setup()` in `init.lua`. This is the direct analogue of a sync-status emblem. — [yazi-rs/plugins](https://github.com/yazi-rs/plugins)

**Flea (Omarchy-specific, new)**
- Flea is a keyboard-first file manager for Omarchy by a developer known as "GM" ([github.com/thisisgm/flea](https://github.com/thisisgm/flea)), first public in early September 2026. Version 0.3 was QML inside Quickshell; 0.4.0 (released 3 November 2026) draws its window with `flea-gui`, a Rust program on GPUI, and has a `--tui` mode. 0.4.0 "runs plugins as separate processes" (a "Shelf" plugin is mentioned) but no plugin API is described. It has colour tags, not emblems, and a built-in `m` action menu with no documented way to add custom actions. — [Starry Hope: Flea on Omarchy](https://www.starryhope.com/linux/flea-file-manager-omarchy/)

### Inferences
- A capability matrix for adapter design, from the verified facts: Nautilus/Nemo/Caja = emblems + dynamic menus + columns via one Python source; Dolphin = emblems + dynamic menus via two compiled C++ plugins that must track KF major versions; Thunar = menus only through thunarx (no extension-driven emblems); COSMIC Files = static user-configured actions only; yazi = status text/glyph in the linemode via a Lua fetcher plus keybound actions.
- Because Nautilus cannot hook activation, an on-demand client cannot make "open a placeholder" an extension-level event. Hydration on open has to happen below the file manager (FUSE read path or equivalent), which makes the file-manager adapter purely cosmetic/command-issuing. That is good for a desktop-agnostic core.
- `ColumnProvider` + `add_string_attribute` gives Nautilus list view a sortable "Availability" column (online-only / local / pinned) cheaply, and `PropertiesModelProvider` gives a text-only properties page. Both are low-risk additions on top of emblems.
- nautilus-python is the lowest-cost first adapter (no compilation, no ABI coupling to Nautilus's soname), at the price of a Python interpreter inside the Nautilus process. A C/Rust `.so` avoids that dependency but must be rebuilt against `libnautilus-extension`.

## 2. Desktop-neutral mechanisms

### Takeaway
There is no single desktop-neutral way to show per-file sync state: GIO `metadata::emblems` is honoured by some GTK file managers but does not refresh live, and libcloudproviders gives an account-level sidebar entry, status and menu in Nautilus and the GTK file chooser only. The genuinely neutral surfaces are the StatusNotifierItem tray, `org.freedesktop.Notifications`, bookmarks, and the Secret Service; per-file state always needs a per-file-manager adapter talking to the daemon.

### Cited Findings

**libcloudproviders (`org.freedesktop.CloudProviders`)**
- libcloudproviders is "a DBus API that allows cloud storage sync clients to expose their services"; its README lists Nextcloud client 2.5 as a server implementation and GNOME Nautilus and elementary OS as clients. — [libcloudproviders README](https://raw.githubusercontent.com/GNOME/libcloudproviders/main/README.md)
- [local] On Arch/Omarchy in November 2026, `nautilus 51.1`, `gtk4` and `gtk3` are all linked against `libcloudproviders.so.0` (`libcloudproviders 0.4.1-1`, "Required By: gtk3 gtk4 nautilus"). So the consumer side is alive in the current Nautilus and in both GTK file choosers as built by Arch. `/usr/share/cloud-providers/` does not exist on this machine, i.e. no provider is registered by default.
- Nautilus displays all registered cloud-provider entries in the sidebar with no way to hide individual ones (a GNOME Discourse proposal asks for per-entry visibility). — [GNOME Discourse: per-entry visibility for cloudproviders](https://discourse.gnome.org/t/per-entry-visibility-control-for-cloudproviders-in-nautilus/33836)
- A 2023 Nautilus issue reported cloud-provider entries reachable from the GTK4 file chooser but missing in Nautilus after the GTK4 port, with users relying on libcloudproviders to manage Nextcloud. — [Nautilus issue 2392](https://gitlab.gnome.org/GNOME/nautilus/-/issues/2392)
- Nautilus's cloudproviders dependency was made build-optional in 2022 "because it is not desired for RHEL", so distro builds can lack it. — [GNOME commits list, Aug 2022](https://lists.gnome.org/archives/commits-list/2022-August/msg01642.html)
- ownCloud desktop client 5.0 dropped libcloudproviders support. — [ownCloud Central thread](https://central.owncloud.org/t/gnome-45-owncloud-desktop-client-45-linux-integration/45493)
- A new implementer in 2026 (wusel) speaks the protocol directly over D-Bus with `zbus` rather than the C library; uses one bus name per account (`org.freedesktop.CloudProviders.wusel.<account>`); reports that the collector scans only `g_get_system_data_dirs()` so the registration file must be system-installed (needs root; Flatpak exports are among scanned dirs); calls the status channel "historically fragile" in Nautilus; and states KDE and other desktops do not consume the protocol. — [wusel 0.4.0 desktop integration](https://wusel.itbh.at/wusel/0.4.0/explanation/desktop-integration.html)
- The original design covers status, name, icon, folder path and custom menus for an account. — [GNOME wiki: CloudProviders](https://wiki.gnome.org/Design/Whiteboards/CloudProviders)

**GIO `metadata::emblems`**
- Thunar reads and writes emblems via the GIO `metadata::emblems` attribute; externally made changes are not picked up until refresh because there is no change notification for metadata. — [Thunar issue 630](https://gitlab.xfce.org/xfce/thunar/-/issues/630)
- A 2026 implementer removed its extended-attribute based status from its Nautilus integration in favour of live socket queries, arguing that status stored on files goes stale and "a file copied out of the mount has no status to carry". — [wusel status protocol](https://wusel.itbh.at/wusel/latest/explanation/status-protocol.html)

**`org.freedesktop.FileManager1`**
- [local] `org.freedesktop.FileManager1` is D-Bus activatable on Omarchy, with the service file owned by `nautilus 51.1-1`. `xdg-mime query default inode/directory` returns `org.gnome.Nautilus.desktop`.

**Tray (StatusNotifierItem) under Hyprland**
- Quickshell's `SystemTrayItem` is "roughly conforming to the kde/freedesktop spec" ("no real spec, we just implemented whatever seemed to actually be used"), exposing `id`, `title`, `icon`, `tooltipTitle`, `tooltipDescription`, `category`, `status`, `onlyMenu`, `hasMenu`, `menu`; menus come via the `Quickshell.DBusMenu` module. — [Quickshell SystemTrayItem docs](https://quickshell.org/docs/types/Quickshell.Services.SystemTray/SystemTrayItem/)
- [local] On Omarchy 4.5 the `quickshell` process owns `org.kde.StatusNotifierWatcher` and an `org.kde.StatusNotifierHost-*` name on the session bus; the bar's tray widget is `/usr/share/omarchy/shell/plugins/bar/widgets/Tray.qml` using `Quickshell.Services.SystemTray`. Comments in that file note that `QsMenuEntry.display()` (platform menus) does not work in Omarchy's shell because it does not use `QApplication`, and the widget implements its own submenu drill-down as a workaround. `libappindicator` and `libayatana-appindicator` are installed.

**Notifications**
- [local] On Omarchy 4.5 `org.freedesktop.Notifications` is owned by `quickshell`; the shell's notification service declares `actionsSupported`, `bodyMarkupSupported`, `bodyHyperlinksSupported`, `imageSupported`, `persistenceSupported` as true. `libnotify` is installed.
- Omarchy 4.0's native notification daemon has popups, do-not-disturb, deduping and a history of the last ten notifications. — [Omarchy v4.0.0 release notes](https://github.com/basecamp/omarchy/releases/tag/v4.0.0)
- Practical portability notes from an implementer: pass icons via the `image-path` hint because GNOME Shell only honours `app_icon` for apps it can resolve; map severity to the urgency hint; restrict notifications to actionable warnings and recoveries; offer a `notify_hook` script for headless systems. — [wusel 0.4.0 desktop integration](https://wusel.itbh.at/wusel/0.4.0/explanation/desktop-integration.html)

**Bookmarks / sidebar**
- [local] `~/.config/gtk-3.0/bookmarks` exists on Omarchy and holds `file:///... Label` lines (Downloads, Projects, Pictures, Videos). Appending a line is the zero-dependency way to get a sidebar entry in Nautilus and GTK file choosers.

**Thumbnailers, indexers and unwanted hydration**
- FUSE has no way to signal "do not hydrate for this reader"; native Windows Cloud Filter and macOS File Provider backends can. A desktop indexer or thumbnailer that reads files triggers hydration of everything it touches. Mitigation used by wusel: `.trackerignore` and `.nomedia` markers in the mount (KDE Baloo ignores them, so users must exclude the folder in Baloo settings); "thumbnailers can still hydrate files". — [wusel: VFS-first](https://wusel.itbh.at/wusel/0.3.0/explanation/vfs-first.html); [wusel 0.4.0 desktop integration](https://wusel.itbh.at/wusel/0.4.0/explanation/desktop-integration.html)
- A FUSE author's request that Nautilus stop thumbnailing FUSE filesystems is tracked as Nautilus issue 1209. — [Nautilus issue 1209](https://gitlab.gnome.org/GNOME/nautilus/-/issues/1209)
- "Local Files Only" thumbnailing did not stop Nautilus thumbnailing files on an NFS mount (old Launchpad report), i.e. kernel-mounted network/FUSE paths count as local. — [Launchpad bug 293311](https://bugs.launchpad.net/ubuntu/+source/nautilus/+bug/293311)
- [local] Omarchy's Nautilus has `org.gnome.nautilus.preferences show-image-thumbnails = 'local-only'`; installed thumbnailers in `/usr/share/thumbnailers/` include ffmpegthumbnailer (video and audio), glycin (image-rs, heif, jxl, svg), papers, evince, gsf-office. `localsearch` (Tracker) is installed and autostarted (`/etc/xdg/autostart/localsearch-3.desktop`), and `sushi` (previewer) is installed.

### Inferences
- For Omarchy as first target, libcloudproviders is worth implementing: Nautilus 51 and GTK3/GTK4 choosers there are all linked against it, and the D-Bus protocol can be served from the daemon without linking the C library (the wusel/zbus precedent). Caveats: registration file must live in a system data dir, which fits a pacman/AUR package but not a per-user install, and status display is reported as fragile. Pair it with a GTK bookmark fallback, taking care not to create a duplicate sidebar entry (the Nextcloud "shown twice in sidebar" forum thread appeared in search results, not fetched).
- `metadata::emblems` is not a viable primary mechanism: no live refresh, per-user gvfs metadata store rather than the file, and on a FUSE mount the semantics are doubtful. Treat as a last-resort fallback for Thunar/PCManFM, if at all.
- An on-demand client on a FUSE/placeholder design must defend against thumbnailers, `localsearch`, `sushi` and Baloo itself. Options that follow from the findings: ship `.trackerignore`/`.nomedia`; in the read path, identify the calling process (FUSE gives the caller PID) and refuse or serve-from-cloud-thumbnail for known thumbnailer/indexer processes; proactively write cloud-provided thumbnails (Microsoft Graph has thumbnail endpoints) into the freedesktop thumbnail cache so the file manager finds a valid thumbnail and never opens the file. The last two are design inferences, not verified practice.
- Tray menus on Omarchy should be flat or shallow: the shell's tray needed a custom workaround for submenus, so deep DBusMenu trees are a risk on Quickshell-based bars.

## 3. How existing multi-desktop sync clients structure this; the Nextcloud socket protocol

### Takeaway
Yes: "daemon owns state and exposes a local socket; thin per-file-manager plugins query it and render" is the consensus (Dropbox, ownCloud/Nextcloud, Insync, and the 2026 newcomer wusel all do it). The Nextcloud/ownCloud socket API is a trivial line-based text protocol over a Unix socket that already includes on-demand verbs (`MAKE_AVAILABLE_LOCALLY`, `MAKE_ONLINE_ONLY`) and server-driven menus, so a new client can speak it and reuse the existing Nautilus/Nemo/Caja script nearly verbatim; the main limits are a coarse status vocabulary and string-typed framing.

### Cited Findings

**Nextcloud socket API: transport and framing**
- Server socket path on Linux: `QStandardPaths::RuntimeLocation + "/" + appName + "/socket"`, i.e. `$XDG_RUNTIME_DIR/Nextcloud/socket`. Windows uses a named pipe; macOS uses XPC instead. — [nextcloud/desktop socketapi.cpp](https://raw.githubusercontent.com/nextcloud/desktop/master/src/gui/socketapi/socketapi.cpp)
- Client side: `AF_UNIX`/`SOCK_STREAM`; path `os.path.join(get_runtime_dir(), appname, "socket")`, falling back to `<tmp>/runtime-<user>/` when `XDG_RUNTIME_DIR` is unset; reconnect every 5000 ms; on connect send `VERSION:\n` then `GET_STRINGS:\n`. — [nextcloud/desktop syncstate.py](https://raw.githubusercontent.com/nextcloud/desktop/master/shell_integration/nautilus/syncstate.py)
- Framing: one message per line, `\n` terminated, fields split on `:` (`action = parts[0]`); values containing `:` are rejoined; multiple paths in one request are joined with ASCII record separator `\x1e`. — [syncstate.py](https://raw.githubusercontent.com/nextcloud/desktop/master/shell_integration/nautilus/syncstate.py)
- The whole extension is rebranded by changing one variable, `appname = 'Nextcloud'` (done by `setappname.sh`); it determines the socket directory, the emblem icon names and the default menu title. — [syncstate.py](https://raw.githubusercontent.com/nextcloud/desktop/master/shell_integration/nautilus/syncstate.py)

**Nextcloud socket API: messages**
- Client -> daemon: `VERSION:`, `GET_STRINGS:`, `RETRIEVE_FILE_STATUS:<path>`, `RETRIEVE_FOLDER_STATUS:<path>`, `GET_MENU_ITEMS:<path>\x1e<path>...`, and menu actions as `<ACTION>:<path>`. Status requests are fire-and-forget; the answer arrives later as a `STATUS` push. — [syncstate.py](https://raw.githubusercontent.com/nextcloud/desktop/master/shell_integration/nautilus/syncstate.py)
- Daemon -> client: `VERSION:<appversion>:1.1`; `STRING:<key>:<value>` (keys used: `CONTEXT_MENU_TITLE`, `SHARE_MENU_TITLE`, `COPY_PRIVATE_LINK_MENU_TITLE`, `EMAIL_PRIVATE_LINK_MENU_TITLE`); `REGISTER_PATH:<path>` (sent per sync root on connect and when a folder becomes syncable); `UNREGISTER_PATH:<path>`; `UPDATE_VIEW:<path>` (after sync state changes: SyncPrepare, Success, Paused, Problem, Error, SetupError); `STATUS:<state>:<path>`; `GET_MENU_ITEMS:BEGIN` ... `MENU_ITEM:<ACTION>:<flags>:<label>` ... `GET_MENU_ITEMS:END`, where flag `d` means disabled. — [socketapi.cpp](https://raw.githubusercontent.com/nextcloud/desktop/master/src/gui/socketapi/socketapi.cpp); [syncstate.py](https://raw.githubusercontent.com/nextcloud/desktop/master/shell_integration/nautilus/syncstate.py)
- Status vocabulary and emblem mapping in the Nautilus script: `OK` -> `<app>_ok`; `SYNC` and `NEW` -> `<app>_sync`; `IGNORE` -> `<app>_warn`; `ERROR` -> `<app>_error`; each with a `+SWM` variant that adds `<app>_a_shared`; `NOP` -> no emblem. — [syncstate.py](https://raw.githubusercontent.com/nextcloud/desktop/master/shell_integration/nautilus/syncstate.py)
- Full server handler list: `RETRIEVE_FOLDER_STATUS`, `RETRIEVE_FILE_STATUS`, `SHARE`, `LEAVESHARE`, `ACTIVITY`, `FILE_ACTIONS`, `ENCRYPT`, `VERSION`, `SHARE_MENU_TITLE`, `GET_STRINGS`, `EDIT`, `FILES_GOVERNANCE_LABELS`, `COPY_PRIVATE_LINK`, `EMAIL_PRIVATE_LINK`, `OPEN_PRIVATE_LINK`, `MAKE_AVAILABLE_LOCALLY`, `MAKE_ONLINE_ONLY`, `RESOLVE_CONFLICT`, `DELETE_ITEM`, `MOVE_ITEM`, `LOCK_FILE`, `UNLOCK_FILE`, `GET_MENU_ITEMS`, `V2/HYDRATE_FILE`. — [socketapi.cpp](https://raw.githubusercontent.com/nextcloud/desktop/master/src/gui/socketapi/socketapi.cpp)
- Virtual-files menu items sent by the daemon: `MENU_ITEM:CURRENT_PIN:d:<availability text>` (a disabled informational row), `MENU_ITEM:MAKE_AVAILABLE_LOCALLY`, `MENU_ITEM:MAKE_ONLINE_ONLY`, enabled or disabled according to the combined availability of the selection. — [socketapi.cpp](https://raw.githubusercontent.com/nextcloud/desktop/master/src/gui/socketapi/socketapi.cpp)
- Newer framings exist alongside the legacy one: `ASYNC_<NAME>:<jobId>|<json>` answered by `RESOLVE|<jobId>|...` / `REJECT|<jobId>|...`, and `V2/<NAME>` with a JSON argument answered by `<NAME>_RESULT:<json>`. — [socketapi.cpp](https://raw.githubusercontent.com/nextcloud/desktop/master/src/gui/socketapi/socketapi.cpp)
- Push filtering: the client "now tries to only push STATUS messages to connections" that previously asked via `RETRIEVE_FILE_STATUS` (commit note). — [Nextcloud-Desktop commit log mirror](https://git.chylex.com/chylex/Nextcloud-Desktop/commits/tag/v3.3.0/shell_integration?page=3)

**Nextcloud extension behaviour worth copying or avoiding**
- Providers used: `Nautilus.MenuProvider` and `Nautilus.InfoProvider` only; menus appear only when every selected file is inside a registered path; `UPDATE_VIEW`/`REGISTER_PATH` invalidate cached extension info for items under the path. — [syncstate.py](https://raw.githubusercontent.com/nextcloud/desktop/master/shell_integration/nautilus/syncstate.py)
- Weak spots: the menu request blocks the Nautilus UI for up to 100 ms waiting for `GET_MENU_ITEMS:END` and falls back to a hard-coded legacy menu on timeout; the protocol version is compared as strings (`>= '1.1'`, flagged "lexicographic!" in the source); the file has no `gi.require_version` call. — [syncstate.py](https://raw.githubusercontent.com/nextcloud/desktop/master/shell_integration/nautilus/syncstate.py)
- Distribution: one Python file serves Nautilus, Nemo and Caja via scripted string replacement, installed into each `*-python/extensions` directory as `syncstate-<AppShortName>.py`. — [shell_integration/nautilus/CMakeLists.txt](https://raw.githubusercontent.com/nextcloud/desktop/master/shell_integration/nautilus/CMakeLists.txt)
- The Dolphin plugin helper derives its socket path from the application name too (commit note); the Dolphin plugin is built against Qt6 when KF6 KIO is present. — [Nextcloud-Desktop mirror, shell_integration/dolphin](https://source-hub.etos-pro.ru/nextcloud/desktop/src/branch/master/shell_integration/dolphin)

**Dropbox**
- Dropbox's daemon exposes Unix sockets under `~/.dropbox/` (`command_socket`, and `iface_socket` used by the hooks library). The Dolphin plugin sends `icon_overlay_file_status\npath\t<canonical path>` and waits for the reply; i.e. a command name line followed by tab-separated key/value argument lines. — [dolphin-plugins fileviewdropboxplugin.cpp (Debian sources)](https://sources.debian.org/src/dolphin-plugins/4%3A16.08.3-1/dropbox/fileviewdropboxplugin.cpp)
- The Nautilus extension also sends `icon_overlay_context_options` to get per-file menu options. — [Launchpad comment on nautilus-dropbox behaviour](https://bugs.qastaging.launchpad.net/syncany/+bug/793768/comments/1)
- The protocol is not an officially supported API (Dropbox staff: no API for querying status this way). — [Dropbox forum](https://www.dropboxforum.com/t5/Discuss-Dropbox-Developer-API/Check-sync-status-of-dropbox-app-programmatically-via-c-or-api/m-p/382518)
- Third parties (Pantheon/elementary Files, Marlin) wrote their own plugins against the same Dropbox sockets (`dropbox-hooks.c`), showing a stable socket protocol attracts community adapters. — [pantheon-files-plugin-dropbox dropbox-hooks.c](https://bazaar.launchpad.net/~elementary-apps/pantheon-files/pantheon-files-plugin-dropbox/view/8/dropbox-hooks.c)

**Insync**
- Insync ships per-file-manager packages (`insync-dolphin` etc.) with separate `kfileitemaction` and `overlayicon` plugins for KF6, and has had recurring breakage threads ("Dolphin overlay icons not working", "does not work with Plasma 6"). — [Insync forum](https://forums.insynchq.com/t/insync-dolphin-does-not-work-with-plasma-6-new-version-available/19800?page=4); [Insync forum: overlay icons](https://forums.insynchq.com/t/dolphin-overlay-icons-not-working-with-proposed-user-workaround/17300)

**wusel (2026 newcomer, most relevant design comparison)**
- Titled "One status protocol for every file manager": daemon serves a Unix-domain socket (`wusel-ipc`) with length-prefixed frames (max 8 MiB), commands `enumerate`, `stat`, `fetch`, `watch`, `changes`, `notices`; `enumerate` returns each child's `state` and `folder_kind` so one call can prime a client cache; the wire carries the full state as a "neutral superset" that each adapter reduces to what its file manager can render; a separate D-Bus `FileChanged` signal drives cache invalidation. FIFOs were rejected (no per-client connections, no peer credentials). Schema negotiation is planned but not implemented. — [wusel status protocol](https://wusel.itbh.at/wusel/latest/explanation/status-protocol.html)
- Only Nautilus (C extension) and the macOS File Provider are implemented; Dolphin, nautilus-python, Nemo and Thunar are "planned". — [wusel 0.4.0 desktop integration](https://wusel.itbh.at/wusel/0.4.0/explanation/desktop-integration.html)

**Sandboxed distribution breaks the pattern**
- Snap/Flatpak/AppImage builds of the Nextcloud client lose file-manager integration (no overlay icons, no context menu in Nautilus, Caja, Nemo or Dolphin) because the host's extension directories are outside the sandbox. — [Nextcloud forum](https://help.nextcloud.com/t/sandboxed-nextcloud-desktop-client-for-linux-and-system-integration/36627)

### Inferences
- Recommended shape for the new client: the core daemon speaks its own richer, versioned protocol (JSON or length-prefixed, with batch `enumerate` and a subscribe/watch stream) and additionally serves a Nextcloud-compatible legacy socket at `$XDG_RUNTIME_DIR/<AppName>/socket`. The compat endpoint lets a rebranded copy of `syncstate.py` (and the Nemo/Caja derivatives, and potentially the Nextcloud Dolphin plugin) work on day one.
- Do not listen on the literal `Nextcloud` socket path: a user may run the real Nextcloud client. Rebrand via `appname`, which also namespaces the emblem icons (`<App>_ok`, `<App>_sync`, ...), which the client must install into the hicolor icon theme.
- The Nextcloud status vocabulary (`OK`, `SYNC`, `NEW`, `IGNORE`, `ERROR`, `+SWM`, `NOP`) has no state for "online-only placeholder" versus "locally available" versus "always keep on this device". A OneDrive on-demand client needs at least: cloud-only, local (evictable), pinned, syncing, error, excluded, shared. Options: extend the compat protocol with new status tokens and ship a forked script whose emblem table knows them (unknown tokens in the stock script would raise a KeyError-style failure or show nothing; not tested), or put the richer states only in the native protocol.
- The context-menu half fits on-demand files with no protocol change: because menus are server-driven (`MENU_ITEM:<ACTION>:<flags>:<label>`), the daemon can return "Free up space" bound to `MAKE_ONLINE_ONLY` and "Always keep on this device" bound to `MAKE_AVAILABLE_LOCALLY`, with a disabled `CURRENT_PIN` row showing current availability, and the stock script will render and dispatch them (it sends `<ACTION>:<path>` back for whatever the daemon listed; confirm the stock script does not whitelist actions).
- Licensing: the Nextcloud/ownCloud shell-integration scripts are GPL-family licensed (not verified in this session). Speaking a wire protocol is not a licensing issue; shipping a modified copy of `syncstate.py` is, so either comply or write a clean-room adapter (it is roughly 300-400 lines).
- Avoid the stock script's 100 ms blocking menu wait: have the adapter keep a per-path cache of state primed by `enumerate`/push, and build menus locally from cached state where possible.

### Gaps
- `toSocketAPIString()` (the authoritative status-string list, in `syncfilestatus.cpp`) was not fetched; the vocabulary above is from the Nautilus script's mapping table and may omit newer tokens.
- ownCloud's client is the origin of this protocol and (per background knowledge, UNVERIFIED) its newer versions changed transport details; whether ownCloud 5/6 still ships Nautilus scripts was not checked.
- Dropbox: reply format (`ok\n key\tvalue... \ndone\n` as I recall, UNVERIFIED), full command list, and the current state of `nautilus-dropbox` under Nautilus 49-51/GTK4 were not sourced.
- MEGA (MEGAsync has nautilus/nemo/thunar/dolphin extension packages), Syncthing-GTK, pCloud (AppImage with its own FUSE mount, no FM plugins as I recall) and Synology Drive (ships a Nautilus extension) were not researched. All UNVERIFIED (background knowledge).
- How the Nextcloud Dolphin plugin talks to the daemon (same text protocol through a shared helper library) is from a commit note only.
- Whether the stock Nextcloud script tolerates unknown `STATUS` tokens and unknown `MENU_ITEM` actions needs a read of the full file or a test.

## 4. GUI toolkit choices for tray / settings / activity UI

### Takeaway
Little was verifiable from fetched sources in this session; the strongest verified signal is local: Omarchy's shell and its house apps are Qt6/QML (Quickshell), Qt6 is already on the machine alongside GTK4/libadwaita, and the tray is a StatusNotifierItem host. Qt6/QML is therefore the path of least resistance for Omarchy-first while remaining native on KDE; the decisive architectural point is that the UI must be a separate optional process from the sync daemon, which makes the toolkit swappable.

### Cited Findings
- Omarchy 4.0 rebuilt the desktop shell in Quickshell (Qt Quick/QML): bar, launcher, menus, notifications, OSDs, control panels, lock screen and polkit agent run as plugins in "a single long-running shell process". Third-party bar widgets install with `omarchy plugin add <git-url>` and are managed under Setup > Plugins; the Omarchy menu is extensible via `~/.config/omarchy/extensions/omarchy-menu.jsonc`; a plugin directory exists at omarchyplugins.com. — [Omarchy v4.0.0 release notes](https://github.com/basecamp/omarchy/releases/tag/v4.0.0)
- Omarchy 4.0 replaced third-party apps with in-house ones (Satty -> Tensaku, Typora -> Omawrite, GNOME Calculator -> Omacalc). — [Omarchy v4.0.0 release notes](https://github.com/basecamp/omarchy/releases/tag/v4.0.0)
- [local] Installed on Omarchy 4.5: `qt6-base`, `qt6-declarative`, `quickshell`, `gtk4`, `gtk4-layer-shell`, `libadwaita`, `libappindicator`, `libayatana-appindicator`, `knotifications`, `libnotify`, `libportal`, `libportal-gtk4`. This machine's Claude Code skill listing describes Omarchy's own apps (named there: Hype, Monologue, Omacut) as "C++ and Qt Quick, compiled with qmake6 and make into a single binary, following the Omarchy theme live, and installed as an Arch package".
- Flea, the community Omarchy file manager, moved from QML-in-Quickshell (0.3) to a Rust GPUI front end (0.4.0), showing the Omarchy ecosystem is not exclusively Qt. — [Starry Hope: Flea on Omarchy](https://www.starryhope.com/linux/flea-file-manager-omarchy/)
- GTK3 and GTK4 cannot be loaded in the same process, and Nautilus extensions cannot show widgets; extension-triggered UI must be a separate program. — [nautilus-python: Migrating to 4.0](https://gnome.pages.gitlab.gnome.org/nautilus-python/nautilus-python-migrating-to-4.html)
- Precedent for a toolkit-free core: wusel implements CloudProviders and notifications directly over D-Bus with `zbus` from the daemon/CLI, with packaged GUI frontends as a separate later layer. — [wusel 0.4.0 desktop integration](https://wusel.itbh.at/wusel/0.4.0/explanation/desktop-integration.html)

### Inferences
- Omarchy-first options, cheapest to richest: (a) no GUI at all: daemon + CLI + notifications + StatusNotifierItem registered directly over D-Bus from the daemon (in Rust, e.g. the `ksni` crate; UNVERIFIED that it is current), with a flat DBusMenu; (b) an Omarchy bar plugin (QML, installed via `omarchy plugin add`) that talks to the daemon's socket/D-Bus for a native-looking status widget and panel; (c) a standalone Qt6/QML app for settings and activity, matching Omarchy's house style and porting unchanged to KDE, and acceptably to GNOME.
- Trade-off summary (reasoned, not sourced): Qt6/QML = native on KDE and Omarchy, good tray support (`QSystemTrayIcon` uses SNI on Linux), LGPL, C++ or bindings (PySide6, cxx-qt); GTK4/libadwaita = native on GNOME only, and has no tray API at all (GTK4 removed `GtkStatusIcon`; a separate SNI implementation is needed), looks foreign on KDE/Omarchy; Tauri = small binaries but depends on WebKitGTK, tray via libayatana-appindicator; Electron = heaviest, tray works via SNI, what Insync-style clients often use (UNVERIFIED); Flutter = GTK3 embedder on Linux, tray via plugins; iced/slint = pure Rust, tray via separate crates, weaker accessibility/IME and theming integration.
- GNOME caveat that affects every toolkit: stock GNOME Shell has no SNI/AppIndicator host without an extension, so the client must be fully usable with no tray (launcher entry opens the status window; libcloudproviders gives Nautilus sidebar status). UNVERIFIED (background knowledge) but long-standing.

### Gaps
- No primary sources were fetched comparing Qt6, GTK4, Tauri, Electron, Flutter, iced or slint; everything in the trade-off inference is background knowledge and should be validated by whoever owns the toolkit decision (especially tray support status of each in late 2026 and Tauri v2's Linux webview story).
- The Omarchy bar plugin API (manifest format, what a plugin may do, IPC to external daemons) was not read; the shell's `README.md` at `/usr/share/omarchy/shell/README.md` and `plugins/` directory on an Omarchy machine are the place to look.
- Whether Omarchy themes are exposed in a form a third-party Qt6/QML app can follow live (the skill description implies yes for house apps) was not investigated.

## 5. Packaging and distribution considerations affecting integration

### Takeaway
File-manager extensions and a FUSE-backed on-demand mount both want a native package (pacman/AUR, deb, rpm): sandboxed formats cannot install host file-manager plugins, and several integration points (Nautilus `.so` extensions, cloud-provider registration, KDE plugins) only load from system directories. On Omarchy the supporting infrastructure is all present: gnome-keyring provides the Secret Service, FUSE 3 is installed, and portals are hyprland+gtk.

### Cited Findings
- Flatpak apps by default have no access to host files except the runtime, the app, `~/.var/app/$FLATPAK_ID` and `$XDG_RUNTIME_DIR/app/$FLATPAK_ID`; host `/usr` is reserved for the runtime; portals are the sanctioned route to host services. — [Flatpak docs: Sandbox Permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html)
- Sandboxed builds (snap, Flatpak, AppImage) of the Nextcloud client lose overlay icons and context menus in Nautilus, Caja, Nemo and Dolphin. — [Nextcloud forum](https://help.nextcloud.com/t/sandboxed-nextcloud-desktop-client-for-linux-and-system-integration/36627)
- Compiled file-manager plugins are coupled to the file manager's toolkit generation: Nautilus API 3 vs 4 (GTK3 vs GTK4), and KF5 vs KF6 for Dolphin, where a distro shipping the wrong build silently loses overlays. — [nautilus-python: Migrating to 4.0](https://gnome.pages.gitlab.gnome.org/nautilus-python/nautilus-python-migrating-to-4.html); [openSUSE bug 1221923](https://lists.opensuse.org/archives/list/bugs@lists.opensuse.org/thread/MUO5Z6HLHN3L2K5ZNBSQXDANE4RGXVBZ)
- libcloudproviders registration must be in a system data directory (root-installed), though Flatpak export directories are among those scanned. — [wusel 0.4.0 desktop integration](https://wusel.itbh.at/wusel/0.4.0/explanation/desktop-integration.html)
- The Dropbox daemon fails to create its `command_socket` when the home directory is on a filesystem that cannot hold sockets, an argument for placing sockets under `$XDG_RUNTIME_DIR` as Nextcloud does. — [nautilus-dropbox issue 54 (via search summary)](https://github-redirect.dependabot.com/dropbox/nautilus-dropbox/issues/54); [socketapi.cpp](https://raw.githubusercontent.com/nextcloud/desktop/master/src/gui/socketapi/socketapi.cpp)
- Omarchy 4.0 pins Chromium-based browsers to the gnome-libsecret password store, i.e. the distro treats gnome-keyring/libsecret as the system secret store. — [Omarchy v4.0.0 release notes](https://github.com/basecamp/omarchy/releases/tag/v4.0.0)
- Omarchy packages install from Omarchy's own pacman repository first (since 4.0.5), and packages can be added with `omarchy pkg add <name>`; a package depending on `omarchy` will not install on plain Arch. — [Starry Hope: What is Omarchy](https://www.starryhope.com/linux/what-is-omarchy/); [Starry Hope: Flea on Omarchy](https://www.starryhope.com/linux/flea-file-manager-omarchy/)
- [local] Secret storage on Omarchy 4.5: `gnome-keyring 1:51.1-1` is a hard dependency of the `omarchy` package; `gnome-keyring-daemon.service` runs as a systemd user service and owns `org.freedesktop.secrets`; `libsecret 0.21.8.2` is installed; `gnome-keyring.portal` provides `org.freedesktop.impl.portal.Secret` (set explicitly in the user portal config). `kwallet` is also installed with `org.kde.kwalletd6` and `org.kde.secretservicecompat` D-Bus activatable but not running.
- [local] Portals on Omarchy 4.5: `xdg-desktop-portal 1.22.1`, `xdg-desktop-portal-hyprland 1.4.1`, `xdg-desktop-portal-gtk 1.15.3`, all running as user services; portal config `default=hyprland;gtk`; backend definition files present: `hyprland.portal`, `gtk.portal`, `gnome-keyring.portal`, `kwallet.portal`. `xdg-document-portal` and `xdg-permission-store` are running.
- [local] FUSE on Omarchy 4.5: `fuse3` and `fuse-common` installed, `fusermount3` 3.18.3; `/etc/fuse.conf` has no active (uncommented) options, so `user_allow_other` is off by default.
- [local] Session plumbing on Omarchy 4.5: Hyprland is launched through `uwsm` as systemd user units (`wayland-wm@hyprland.desktop.service`), with `dbus-broker` and a populated systemd user session; XDG autostart entries in `/etc/xdg/autostart` are honoured (for example one shows up as `app-remmina\x2dapplet@autostart.service`), so both a systemd user unit and an XDG autostart `.desktop` file work for starting a daemon.
- [local] Arch already packages `nextcloud-client 2:35.0.0-2` in `extra`, a convenient reference PKGBUILD for how a sync client and its shell-integration files are split and installed.

### Inferences
- Packaging plan that follows: one native package for the daemon/CLI (systemd user unit, `graphical-session.target`-aware), plus small optional sub-packages per adapter (`-nautilus`, `-nemo`, `-caja`, `-dolphin`, `-yazi`) as Nextcloud, Insync and MEGA do. AUR first; later an Omarchy-repo package for `omarchy pkg add`.
- Python adapters for Nautilus/Nemo/Caja can alternatively be dropped per-user into `~/.local/share/<fm>-python/extensions/` by the client itself with no root and no package (Omarchy itself does this for Nautilus: section 6), which is the only viable route for an AppImage or a user-level install. It still requires the distro's `nautilus-python` package to be present.
- Flatpak is a poor primary format for this product: a FUSE mount needs `fusermount3` on the host and a mountpoint visible outside the sandbox, and file-manager plugins need host directories. If a Flatpak is ever offered, it would cover the GUI only, with daemon and adapters native. (The FUSE-in-Flatpak restriction itself is UNVERIFIED in this session.)
- Use the Secret Service API via libsecret (or a pure D-Bus client such as the Rust `oo7`/`secret-service` crates; UNVERIFIED currency) for OAuth refresh tokens: it is served by gnome-keyring on Omarchy/GNOME and, per background knowledge, by KWallet's Secret Service compatibility on Plasma 6 (the `org.kde.secretservicecompat` name seen locally is consistent with that). Provide an encrypted-file fallback for headless sessions where no collection is unlocked (a risk on auto-login setups where the login keyring is not unlocked by PAM; not checked for Omarchy's SDDM configuration).
- With `user_allow_other` off, a FUSE mount is visible only to the mounting user; that is fine for desktop use but means root-run tools and some sandboxed apps (via the document portal) will not see the files.

### Gaps
- AppImage, deb and rpm specifics (extension directory multiarch paths such as `/usr/lib/x86_64-linux-gnu/nautilus/extensions-4`, Fedora's nautilus-python packaging, immutable distros like Silverblue where `/usr` is read-only and layered packages or sysexts are needed) were not researched.
- Whether Omarchy's SDDM login unlocks the gnome-keyring login collection automatically (PAM `pam_gnome_keyring`) was not checked; it determines whether the daemon can read tokens at session start without a prompt.
- How portal-mediated file choosers (used by Flatpak apps and by apps that opt in) present a FUSE-backed cloud folder, and whether the document portal's own FUSE layer triggers hydration on selection, was not investigated.
- Kernel-side alternatives to FUSE that affect integration (fanotify pre-content hooks merged in recent kernels, which let a daemon fill files on first access on a normal filesystem) are out of this note's scope but change the thumbnailer/hydration story; flagged for the researcher covering the on-demand mechanism.

## 6. Omarchy specifically: default components and what they imply for a first integration

### Takeaway
The brief's premise is out of date: since Omarchy 4.0 (August 2026) Waybar and Mako are gone, replaced by a single Quickshell-based shell that provides the bar, the StatusNotifierItem tray, and the notification daemon. Nautilus (51.1, with nautilus-python preinstalled and already used by Omarchy's own extensions) is still the default file manager as of Omarchy 4.5.0, but its replacement has been publicly signalled, so the Nautilus adapter should be thin and the core protocol should be the investment.

### Cited Findings
- Omarchy v4.0.0 ("The Quattro Release", dated 14 August; year inferred as 2026) removed Waybar, Walker, Mako, SwayOSD, hyprlock, hypridle, swaybg and polkit-gnome ("all gone") in favour of a shell rebuilt in Quickshell; Wi-Fi moved from iwd to NetworkManager. — [Omarchy v4.0.0 release notes](https://github.com/basecamp/omarchy/releases/tag/v4.0.0)
- Older documentation still lists Waybar and Mako (for example the Omarchy manual's theming text and community package lists); these predate 4.0 and conflict with the release notes and with the local inspection below. — [The Omarchy Manual (as surfaced in search)](https://learn.omacom.io/2/the-omarchy-manual.md); contradicted by [Omarchy v4.0.0 release notes](https://github.com/basecamp/omarchy/releases/tag/v4.0.0)
- [local] The `omarchy 4.5.0-3` package's upstream URL is `https://github.com/omacom/omarchy` (the project appears to have moved from `basecamp/omarchy`; release pages exist under both names per newreleases.io listings). Its hard dependencies include `hyprland`, `quickshell`, `uwsm`, `sddm`, `xdg-desktop-portal-hyprland`, `pipewire`, `wireplumber`, `gnome-keyring`. `waybar`, `mako` and `swayosd` are not installed.
- [local] File manager: `nautilus 51.1-1` is installed and is the `inode/directory` default (`org.gnome.Nautilus.desktop`); `nautilus-python 4.2.0-1` is installed (explicitly, not as a dependency); `sushi`, `gvfs` 1.62.0 (+mtp, nfs, smb), `ffmpegthumbnailer`, `localsearch` and `tinysparql` are present.

This is a first-party precedent for exactly the adapter style a sync client needs, including the install location.
- [local] Bar/tray/notifications: a single `quickshell` process owns `org.freedesktop.Notifications`, `org.kde.StatusNotifierWatcher` and a StatusNotifierHost name; shell sources are at `/usr/share/omarchy/shell/` (`shell.qml`, `plugins/bar/widgets/Tray.qml`, `plugins/notifications/Service.qml`). Notification capabilities declared: actions, body markup, hyperlinks, images, persistence.
- [local] Keyring: gnome-keyring daemon running and owning `org.freedesktop.secrets`. Portals: hyprland + gtk backends, `default=hyprland;gtk`, Secret portal mapped to gnome-keyring. ### Inferences
- First integration on Omarchy can be built entirely from pieces already on the machine, with no new system dependencies: (1) a nautilus-python extension (InfoProvider emblems + MenuProvider for "Free up space" / "Always keep on this device" + optional ColumnProvider) installed to `~/.local/share/nautilus-python/extensions/` or `/usr/share/nautilus-python/extensions/`; (2) emblem icons installed into the hicolor theme; (3) a StatusNotifierItem for the Quickshell tray with a flat menu; (4) `org.freedesktop.Notifications` with actions; (5) Secret Service for tokens; (6) a libcloudproviders D-Bus provider and/or a GTK bookmark for the sidebar; (7) a systemd user service started with the uwsm-managed graphical session.
- An Omarchy-native extra would be a Quickshell bar plugin (QML) installable via `omarchy plugin add`, showing sync state without relying on the generic tray.
- The signalled move away from Nautilus is the strongest argument for the desktop-agnostic core: if Omarchy switches default to Flea or another newcomer, the Nautilus adapter loses its Omarchy audience (while staying valid for GNOME/Ubuntu/Fedora). Since Flea 0.4 has out-of-process plugins and depends on `quickjs-ng` and `python-gobject`, a socket-speaking adapter is plausibly feasible, but nothing about its plugin API is documented; engaging with the Flea author early (asking for a per-file status-badge hook and a context-action hook) could be worthwhile.
- Since changing the default file manager on Omarchy also swaps the portal file chooser (per the `flea --default` procedure), file-chooser behaviour over the cloud folder may differ between Nautilus-default and Flea-default systems; test both.
- Hydration risk on stock Omarchy is concrete: `localsearch` autostarts, `sushi` previews on spacebar, and `ffmpegthumbnailer`/glycin/papers thumbnailers are installed, with Nautilus thumbnails set to `local-only` (which historically still covers kernel-mounted FUSE paths). The mount must ship indexer-exclusion markers and a thumbnailer strategy from day one.

### Gaps
- The Omarchy manual (omarchy.org / learn.omacom.io) and the repo's package lists were not fetched directly; the component list above rests on the v4.0.0 release notes plus local inspection of one Omarchy 4.5.0 machine, which may have user customisations (for example `kwallet`, `knotifications` and `signon-kwallet-extension` are installed here and may or may not be Omarchy defaults; `nautilus-python` is marked "explicitly installed", which is consistent with an installer package list but not proof).
- `/usr/share/omarchy/version` reads `4.0.0.alpha` on this machine while the package is 4.5.0-3; unexplained, probably a stale file, not investigated.
- DHH's 11 September 2026 statement is reported via a secondary article; the original post was not fetched. Which other file managers are candidates, and any timeline, are unknown.
- Flea's plugin protocol, whether it shows any per-file badges from external sources, and whether it implements `org.freedesktop.FileManager1` are undocumented in the sources read; its GitHub repo (github.com/thisisgm/flea) was not fetched.
- Whether Omarchy's Nautilus build shows libcloudproviders sidebar entries correctly in 51.1 was not tested (only the linkage was verified).
